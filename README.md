# Контроль качества данных по целям сотрудников

Backend-сервис для проверки целей и ключевых результатов, хранения истории прогонов, расчёта метрик и выдачи результатов через REST API. Разработка ведётся поэтапно с ИИ-ассистентом.

**Текущее состояние:** Spring Boot, четыре доменных правила ККД, схема PostgreSQL, обратимые миграции Liquibase, ограничения и защита истории, функции и VIEW, автоматические тесты. Compose пока запускает только БД. Выполнение прогонов из Java и демонстрационные данные доступны. Метрики/дельта, бизнес-API и CI — следующие шаги. Frontend исключён из согласованного объёма.

## Подготовка

Нужны JDK 21 и Docker с Compose. Maven Wrapper использует Maven 3.9.11; отдельная установка Maven не нужна. При первом использовании нужен доступ к Maven Central и Docker Registry. В Linux/macOS Wrapper скачивает Maven через wget либо curl; распаковывает через unzip или tar. JAVA_HOME должен указывать на установленный JDK 21.

Команды ниже предназначены для Linux/macOS. Из корня проекта один раз создайте локальную конфигурацию:

```sh
cp .env.example .env
```

Пароль в примере предназначен только для локальной разработки. `.env` исключён из Git. Spring Boot и Maven не читают его автоматически: в каждом новом терминале перед запуском приложения или команд Liquibase загрузите переменные:

```sh
set -a
. ./.env
set +a
docker compose up -d --wait db
```

БД доступна только на localhost:5432. Если порт занят, согласованно измените DB_PORT и порт в DB_URL. Если меняете DB_NAME, измените также имя БД в DB_URL. Compose использует именованный том: остановка контейнера сохраняет данные. Значения POSTGRES_* применяются при первой инициализации пустого тома, а не меняют пользователя существующей БД.

## Сборка и тесты

Из backend/ при настроенном JAVA_HOME:

```sh
./mvnw --version
./mvnw -B verify
```

Полный test/verify требует доступный Docker: Testcontainers создаёт отдельные временные PostgreSQL 17.11 и удаляет их после проверки. Тесты не используют БД из .env. Недоступность Docker приводит к ошибке, а не скрытому пропуску проверок.

Без Docker можно проверить только доменную логику:

```sh
./mvnw -B -Dtest=GoalSnapshotTest,KeyResultSnapshotTest,IssueTest,DataQualityCheckerTest,DataQualityRulesTest test
```

При compile/test/verify автоматически проверяются JDK 21 и формат Java. Формат — Google Java Format 1.28.0, AOSP. Для отдельной проверки используйте `./mvnw spotless:check`, для исправления — `./mvnw spotless:apply`. Обычная сборка файлы не переписывает. `--version` только показывает окружение.

Полный verify создаёт исполняемый JAR в backend/target/. На текущей версии пройдено 143 сценария без ошибок и пропусков: 99 доменных, 7 проверок команд и 37 с PostgreSQL (схема, конкуренция, цикл миграций, выполнение прогонов, демо и Spring-контекст).

На Windows вместо `./mvnw` используйте `.\mvnw.cmd` в PowerShell либо `mvnw.cmd` в cmd. Переменные окружения задаются средствами выбранной оболочки. Windows и запуск по инструкции в чистом окружении пока не проверены.

## Локальный запуск

Сначала запустите БД и экспортируйте переменные, как показано выше. Затем из backend/:

```sh
./mvnw spring-boot:run
```

Или после успешной verify:

```sh
"$JAVA_HOME/bin/java" -jar target/kkd-service-0.0.1-SNAPSHOT.jar
```

Liquibase при старте применяет отсутствующие миграции. По умолчанию HTTP-порт 8080, другой задаётся SERVER_PORT. Для остановки приложения используйте Ctrl+C. Бизнес-маршруты ещё не реализованы: GET /api/runs пока возвращает стандартный 404.

Для остановки локальной БД без удаления данных из корня:

```sh
docker compose stop db
```

## Демо и выполнение прогонов

По умолчанию приложение только запускается и применяет миграции: демо и автоматический прогон выключены. Для демонстрации после verify выполните из backend/ с экспортированными переменными БД:

```sh
"$JAVA_HOME/bin/java" -jar target/kkd-service-0.0.1-SNAPSHOT.jar \
  --spring.main.web-application-type=none \
  --kkd.demo.enabled=true
```

Команда создаёт 3 подразделения, 24 цели и два завершённых прогона: `demo-2026-10-19` (10 проблем) и `demo-2026-10-26` (8 проблем). Все результаты вычисляются правилами Java, а не вставляются готовыми. В наборе есть все четыре правила и примеры новых, сохраняющихся и исправленных проблем; выдача метрик и дельты через API ещё не реализована.

Демо требует пустой БД либо уже завершённой демопары. Повторный запуск не создаёт дубли и не переписывает текущие источники; дополнительные обычные прогоны сохраняются. Если данные уже есть, а демопары нет, команда завершается ошибкой без изменения данных. Создание обоих демопрогонов атомарно: ошибка второго откатывает весь набор, включая первый.

Для запуска HTTP-приложения с демо:

```sh
KKD_DEMO_ENABLED=true ./mvnw spring-boot:run
```

Для отдельного нового прогона по текущим данным:

```sh
"$JAVA_HOME/bin/java" -jar target/kkd-service-0.0.1-SNAPSHOT.jar \
  --spring.main.web-application-type=none \
  --kkd.demo.enabled=false \
  --kkd.run.enabled=true \
  --kkd.run.date=2026-10-27
```

Без `--kkd.run.date` используется сегодняшняя дата UTC. Каждый обычный вызов создаёт новый UUID. Для сравнения выбирается последний завершённый прогон с датой снимка не позже заданной. Повторный прогон с той же датой разрешён. Демо и одиночный прогон нельзя включать одновременно; некорректная дата отклоняется до создания прогона. Расписание не включено и пока не реализовано.

Команды без HTTP завершаются после выполнения. В логе выводятся ID, дата, статус, сравниваемый прогон и число проблем. Ошибка расчёта/сохранения откатывает частичные результаты и сохраняет FAILED; команда завершается с ненулевым кодом. При недоступности БД или ошибке commit сохранение FAILED не гарантируется. Параллельные прогоны сериализуются блокировкой; ожидание ограничено 10 секундами. Для согласованного снимка запись в таблицы источника блокируется до конца транзакции.

Пока API не реализован, результаты можно посмотреть из корня проекта:

```sh
docker compose exec -T db psql -U "$DB_USERNAME" -d "$DB_NAME" -c \
  'SELECT r.id, r.snapshot_date, r.status, r.compared_to_id, s.issues_count FROM kkd.kkd_run r JOIN kkd.run_statistics s ON s.run_id=r.id ORDER BY r.snapshot_date,r.id;'
```

## Проверка наката, отката и повторного наката

Выполняйте этот цикл на отдельной тестовой БД с остановленным приложением: откат удаляет всю схему kkd вместе с исходными данными, снимками и историей прогонов. Укажите в DB_URL/DB_USERNAME/DB_PASSWORD эту БД и экспортируйте переменные. Из backend/:

```sh
./mvnw -B liquibase:update
./mvnw -B liquibase:rollback -Dliquibase.rollbackTag=kkd-baseline
./mvnw -B liquibase:update
./mvnw -B liquibase:update
```

Первый накат создаёт девять бизнес-таблиц, четыре записи справочника, функции, триггеры и VIEW. Откат к baseline удаляет бизнес-схему и все пять записей изменений (включая сам tagDatabase); служебные таблицы Liquibase в public остаются пустыми. Повторный накат восстанавливает схему; последующий update ничего не дублирует. Это проверено отдельными Maven-процессами на PostgreSQL 17.11. Интеграционный тест дополнительно сравнивает полную структуру до и после отката, включая защищённую историю.

Все способы запуска используют один logicalFilePath и служебную схему public. Это предотвращает появление второй истории, когда имя пользователя БД совпадает с бизнес-схемой kkd. Применённые миграции в дальнейшем нужно расширять новыми changeset.

## Что проверено

- Полная сборка на JDK 21, тесты и форматирование; создан исполняемый JAR.
- Реальные PostgreSQL 17.11: ограничения, точность весов, связи внутри снимков, циклы, потомки, неизменяемость и конкурирующая запись/завершение.
- Накат → откат → повторный накат и идемпотентный update через Maven Plugin.
- Команды собранного JAR: обычный старт без записи, создание/повтор демо, отдельный прогон, некорректная дата, конфликт режимов и FAILED с ненулевым кодом завершения.
- Compose с отдельным временным томом; запуск JAR на уже мигрированной БД, неизменная история и ожидаемый 404. Проверочные процессы остановлены, временный том удалён.
- Отклонение JDK 18 и неверного формата, запуск через spring-boot:run.

## Реализованные правила

Все правила работают только для активных целей и их КР.

| Код | Условие | Важность |
| --- | --- | --- |
| GOAL_NO_OWNER | Нет ответственного: null, пустая или пробельная строка | critical |
| GOAL_NO_KR | Нет ни одного КР | critical |
| KR_WEIGHTS_SUM | КР есть, сумма весов численно отличается от 100 | major |
| KR_STALE_PROGRESS | Нет даты обновления факта либо прошло больше 45 календарных дней до даты снимка | minor |

Цель без КР не получает дополнительную проблему суммы весов. Ровно 45 дней допустимо; будущая дата не устаревшая. Вес считается через BigDecimal без округления; диапазон отдельного веса выбранными правилами не проверяется. Проблема КР содержит ID связанной цели и подразделения.

DataQualityChecker — обычный Java-компонент без Spring, SQL и обращения к системным часам. Некорректный вход отклоняется до выполнения правил через IllegalArgumentException, без частичного результата. Проверка циклов и SQL-функция потомков реализованы в БД; агрегация метрик по дочерним подразделениям ещё не реализована.
