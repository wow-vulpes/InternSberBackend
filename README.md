# Контроль качества данных по целям сотрудников

Java backend для контроля качества целей сотрудников: четыре правила ККД, неизменяемая история прогонов, метрики и сравнение результатов через REST API.

Java 21 · Spring Boot 3.5.16 · PostgreSQL 17.11 · Liquibase · Maven · Docker Compose.

Согласованный объём — самостоятельный backend без frontend. Установка на ИФТ и интеграция с корпоративными сервисами требуют доступа и материалов, которые не предоставлены.

## Быстрый запуск в Docker

Нужны Docker с Compose v2 и доступ к Maven Central/Docker Registry при первой сборке. Из корня проекта:

```sh
cp .env.example .env
docker compose up --build -d --wait
```

Локальные JDK и Maven для этого варианта не нужны. После завершения команда подтверждает готовность БД и приложения: миграции и оба демопрогона уже завершены. API доступен по адресу [http://localhost:8080/api/runs](http://localhost:8080/api/runs). Начальная сборка скачивает зависимости и может занять несколько минут.

Для PowerShell на Windows первая команда — `Copy-Item .env.example .env`, команда Docker такая же. В примерах HTTP ниже используйте `curl.exe`; для переноса строк PowerShell использует обратный апостроф вместо `\`. Windows отдельно не проверен.

Compose читает `.env` автоматически. SERVER_PORT задаёт внешний порт приложения, DB_PORT — внешний порт БД; оба доступны только через localhost. Внутри сети приложение всегда подключается к `db:5432`, поэтому локальный DB_URL на Compose не влияет. Для пустой БД без демо задайте COMPOSE_DEMO_ENABLED=false. Этот флаг независим от KKD_DEMO_ENABLED, используемого при запуске Java.

Повторный запуск сохраняет историю и не дублирует демо. Запуск с включённым демо на заполненной БД без демопары отклоняется; используйте COMPOSE_DEMO_ENABLED=false для своих данных. Значения DB_NAME/DB_USERNAME/DB_PASSWORD инициализируют только новый том.

```sh
docker compose logs --tail=100 app
docker compose down
```

`down` сохраняет том с данными. Перед локальным запуском Java остановите контейнер app (`docker compose stop app`), чтобы освободить порт 8080.

## Подготовка для локального запуска Java

Нужны JDK 21 и Docker с Compose. Maven Wrapper использует Maven 3.9.11; отдельная установка Maven не нужна. При первом использовании нужен доступ к Maven Central и Docker Registry. В Linux/macOS Wrapper скачивает Maven через wget либо curl; распаковывает через unzip или tar. JAVA_HOME должен указывать на установленный JDK 21.

Команды ниже предназначены для Linux/macOS. Из корня проекта один раз создайте локальную конфигурацию:

```sh
cp .env.example .env
```

Пароль в примере предназначен только для локальной разработки. `.env` исключён из Git. Spring Boot и Maven не читают его автоматически: в каждом новом терминале перед запуском приложения или команд Liquibase загрузите переменные:

```sh
set -a
. ./.env
set +a
docker compose up -d --wait db
```

БД доступна только на localhost:5432. Если порт занят, согласованно измените DB_PORT и порт в DB_URL. Если меняете DB_NAME, измените также имя БД в DB_URL. Compose использует именованный том: остановка контейнера сохраняет данные. Значения POSTGRES_* применяются при первой инициализации пустого тома, а не меняют пользователя существующей БД.

## Сборка и тесты

Из backend/ при настроенном JAVA_HOME:

```sh
./mvnw --version
./mvnw -B verify
```

Полный test/verify требует доступный Docker: Testcontainers создаёт отдельные временные PostgreSQL 17.11 и удаляет их после проверки. Тесты не используют БД из .env. Недоступность Docker приводит к ошибке, а не скрытому пропуску проверок.

Без Docker можно проверить только доменную логику:

```sh
./mvnw -B -Dtest=GoalSnapshotTest,KeyResultSnapshotTest,IssueTest,DataQualityCheckerTest,DataQualityRulesTest,QualityMetricsCalculatorTest test
```

При compile/test/verify автоматически проверяются JDK 21 и формат Java. Формат — Google Java Format 1.28.0, AOSP. Для отдельной проверки используйте `./mvnw spotless:check`, для исправления — `./mvnw spotless:apply`. Обычная сборка файлы не переписывает. `--version` только показывает окружение.

Полный verify создаёт исполняемый JAR в backend/target/. На текущей версии пройдено 255 сценариев без ошибок и пропусков: 122 доменных, 7 проверок команд, 3 проверки обработки ошибок и 123 с PostgreSQL (схема, конкуренция, цикл миграций, прогоны, демо, метрики/дельта, HTTP-контракты и Spring-контекст).

На Windows вместо `./mvnw` используйте `.\mvnw.cmd` в PowerShell либо `mvnw.cmd` в cmd. Переменные окружения задаются средствами выбранной оболочки. Windows отдельно не проверен. Запуск контейнера проверен на Linux из чистой копии файлов Git и с новой БД; Docker-кэш и доступ к сети были доступны.

## Локальный запуск

Сначала запустите БД и экспортируйте переменные, как показано выше. Затем из backend/:

```sh
./mvnw spring-boot:run
```

Или после успешной verify:

```sh
"$JAVA_HOME/bin/java" -jar target/kkd-service-0.0.1-SNAPSHOT.jar
```

Liquibase при старте применяет отсутствующие миграции. По умолчанию HTTP-порт 8080, другой задаётся SERVER_PORT. Для остановки приложения используйте Ctrl+C. GET /api/runs возвращает список прогонов; до создания данных это пустой массив.

Для остановки локальной БД без удаления данных из корня:

```sh
docker compose stop db
```

## Демо и выполнение прогонов

При локальном запуске Java по умолчанию приложение только запускается и применяет миграции: демо и автоматический прогон выключены. Для демонстрации после verify выполните из backend/ с экспортированными переменными БД:

```sh
"$JAVA_HOME/bin/java" -jar target/kkd-service-0.0.1-SNAPSHOT.jar \
  --spring.main.web-application-type=none \
  --kkd.demo.enabled=true
```

Команда создаёт 3 подразделения, 24 цели и два завершённых прогона: `demo-2026-10-19` (10 проблем) и `demo-2026-10-26` (8 проблем). Все результаты вычисляются правилами Java, а не вставляются готовыми. В наборе есть все четыре правила и примеры новых, сохраняющихся и исправленных проблем; метрики, дельта и список проблем доступны через HTTP API.

Демо требует пустой БД либо уже завершённой демопары. Повторный запуск не создаёт дубли и не переписывает текущие источники; дополнительные обычные прогоны сохраняются. Если данные уже есть, а демопары нет, команда завершается ошибкой без изменения данных. Создание обоих демопрогонов атомарно: ошибка второго откатывает весь набор, включая первый.

Для запуска HTTP-приложения с демо:

```sh
KKD_DEMO_ENABLED=true ./mvnw spring-boot:run
```

Для отдельного нового прогона по текущим данным:

```sh
"$JAVA_HOME/bin/java" -jar target/kkd-service-0.0.1-SNAPSHOT.jar \
  --spring.main.web-application-type=none \
  --kkd.demo.enabled=false \
  --kkd.run.enabled=true \
  --kkd.run.date=2026-10-27
```

Из корня проекта тот же новый прогон можно выполнить в контейнере при работающей БД:

```sh
docker compose run --rm --no-deps app \
  --spring.main.web-application-type=none \
  --kkd.demo.enabled=false \
  --kkd.run.enabled=true \
  --kkd.run.date=2026-10-27
```

На неизменённом демонаборе этот прогон содержит 9 проблем: KR12 переходит с 45 на 46 дней без обновления. Относительно 26 октября — 1 новая, 8 сохраняющихся, 0 исправленных проблем. Старые отчёты сохраняются. Каждый повтор команды создаёт новый прогон; для примера первого сравнения используйте свежий демонабор.

Без `--kkd.run.date` используется сегодняшняя дата UTC. Каждый обычный вызов создаёт новый UUID. Для сравнения выбирается последний завершённый прогон с датой снимка не позже заданной. Повторный прогон с той же датой разрешён. Демо и одиночный прогон нельзя включать одновременно; некорректная дата отклоняется до создания прогона. Расписание не включено и пока не реализовано.

Команды без HTTP завершаются после выполнения. В логе выводятся ID, дата, статус, сравниваемый прогон и число проблем. Ошибка расчёта/сохранения откатывает частичные результаты и сохраняет FAILED; команда завершается с ненулевым кодом. При недоступности БД или ошибке commit сохранение FAILED не гарантируется. Параллельные прогоны сериализуются блокировкой; ожидание ограничено 10 секундами. Для согласованного снимка запись в таблицы источника блокируется до конца транзакции.

Для проверки состояния БД напрямую из корня проекта (для стандартных DB_USERNAME=kkd и DB_NAME=kkd; при изменении замените их в команде):

```sh
docker compose exec -T db psql -U kkd -d kkd -c \
  'SELECT r.id, r.snapshot_date, r.status, r.compared_to_id, s.issues_count FROM kkd.kkd_run r JOIN kkd.run_statistics s ON s.run_id=r.id ORDER BY r.snapshot_date,r.id;'
```

## Метрики и сравнение

`SummaryService.summary(runId, unitId)` вычисляет результаты для завершённого прогона и выбранного подразделения вместе со всеми потомками. Источник — сохранённые снимки; изменение текущих данных и новые прогоны не меняют исторический отчёт. HTTP endpoint — GET /api/kkd/summary.

Три метрики: доля корректных активных целей, число уникальных активных целей с проблемами и общее число проблем. Нарушения КР делают связанную цель некорректной; несколько проблем одной цели учитываются в счётчике целей один раз. Неактивные цели исключаются из числителя, знаменателя и проблем.

Для U1 во втором демопрогоне относительно первого:

| Метрика | Сейчас | Раньше | Дельта | Результат |
| --- | --- | --- | --- | --- |
| Доля корректных целей | 65.2% | 65.2% | 0.0 п.п. | Без изменений |
| Цели с проблемами | 8 | 8 | 0 | Без изменений |
| Проблемы | 8 | 10 | −2 | Улучшение |

Проблемы: 3 новые, 5 сохраняющихся, 5 исправленных; текущие важности critical/major/minor — 3/2/3. Важность каждой метрики равна самой серьёзной текущей проблеме выбранной области, без проблем — null. Произвольные пороги качества не используются.

Доля округляется до одного десятичного знака HALF_UP. Дельта — разность показанных значений; рост доли и снижение счётчиков считаются улучшением. Без прошлого прогона previous/delta/trend и счётчики изменений равны null. При отсутствии активных целей доля равна null, счётчики — 0.

Иерархия берётся отдельно из каждого снимка. У нового подразделения прошлая область пуста: счётчики 0, доля null. Перенос, деактивация и удаление целей могут убрать проблему из выбранной области; категория «исправленные» означает отсутствие в текущей выборке. Подробные контракты и граничные случаи описаны в [дизайне](specs/design.md).

Проверки расчёта без Docker из backend/:

```sh
./mvnw -B -Dtest=QualityMetricsCalculatorTest test
```

Проверка на реальном PostgreSQL, включая демо и изменения иерархии (нужен Docker):

```sh
./mvnw -B -Dtest=SummaryServiceIntegrationTest test
```

## REST API

Запустите приложение с демо, как показано выше. Примеры используют порт 8080; если SERVER_PORT изменён, замените порт в URL.

```sh
curl -sS 'http://localhost:8080/api/runs'

curl -sS --get 'http://localhost:8080/api/kkd/summary' \
  --data-urlencode 'run_id=demo-2026-10-26' \
  --data-urlencode 'unit_id=U1'

curl -sS --get 'http://localhost:8080/api/kkd/issues' \
  --data-urlencode 'run_id=demo-2026-10-26' \
  --data-urlencode 'unit_id=U2' \
  --data-urlencode 'rule=KR_STALE_PROGRESS' \
  --data-urlencode 'severity=minor' \
  --data-urlencode 'limit=1' \
  --data-urlencode 'offset=1'
```

- `/api/runs` — массив всех прогонов, новые по времени начала первыми, при равенстве — ID по убыванию. Включает running/completed/failed; число проблем незавершённых и неуспешных прогонов равно null.
- `/api/kkd/summary` — run, compared_to, unit, metrics, issues_by_severity, delta. run_id и unit_id обязательны. На демо U1: 65.2% корректных целей, 8 целей с проблемами, 8 проблем, дельта проблем 3/5/5.
- `/api/kkd/issues` — {items,total,limit,offset}. run_id обязателен, unit_id/rule/severity необязательны и сочетаются через AND. unit_id включает потомков снимка. Пример выше вернёт KR11 и total=2.

Порядок проблем: goal_id → rule_code → object_type → object_id. Названия объектов и подразделений берутся из снимков. limit по умолчанию 50, диапазон 1–200; offset по умолчанию 0, диапазон 0–2147483647. total учитывает все фильтры до пагинации. Пустая страница за концом выборки — нормальный ответ с сохранённым total.

JSON использует snake_case, правила — верхний регистр, остальные перечисления — нижний. Например, object_type=key_result, severity=minor, trend=improved. Для фильтра severity регистр не важен, для кода rule важен. Неизвестные, повторные и пустые параметры отклоняются; ID не преобразуются в UUID и не обрезаются.

Сводка и проблемы доступны только для completed. Ошибки имеют общий формат:

```json
{"error":{"code":"INVALID_PARAMETER","message":"limit must be between 1 and 200"}}
```

| HTTP | Ситуация | error.code |
| --- | --- | --- |
| 404 | Неизвестный прогон/подразделение | RUN_NOT_FOUND / UNIT_NOT_FOUND |
| 422 | Ошибка параметров | INVALID_PARAMETER |
| 422 | Прогон ещё не завершён или завершился ошибкой | RUN_NOT_COMPLETED |
| 405 | Неподдерживаемый HTTP-метод | METHOD_NOT_ALLOWED |
| 406 | Accept не допускает JSON | NOT_ACCEPTABLE |
| 500 | Непредвиденная ошибка сервера | INTERNAL_ERROR |

Ответ 500 содержит только общее сообщение, без SQL, паролей и трассировок. Чтобы увидеть заголовки и код ошибки:

```sh
curl -i 'http://localhost:8080/api/kkd/issues?run_id=demo-2026-10-26&limit=201'
```

Полные поля ответов и примеры JSON — в [спецификации API](specs/design.md#rest-api). Запуск прогонов и изменение источников через HTTP не предусмотрены.

Для проверки HTTP-контрактов из backend/ (нужен Docker):

```sh
./mvnw -B -Dtest=KkdApiIntegrationTest,ApiExceptionHandlerTest test
```

## Проверка наката, отката и повторного наката

Выполняйте этот цикл на отдельной тестовой БД с остановленным приложением: откат удаляет всю схему kkd вместе с исходными данными, снимками и историей прогонов. Укажите в DB_URL/DB_USERNAME/DB_PASSWORD эту БД и экспортируйте переменные. Из backend/:

```sh
./mvnw -B liquibase:update
./mvnw -B liquibase:rollback -Dliquibase.rollbackTag=kkd-baseline
./mvnw -B liquibase:update
./mvnw -B liquibase:update
```

Первый накат создаёт девять бизнес-таблиц, четыре записи справочника, функции, триггеры и VIEW. Откат к baseline удаляет бизнес-схему и все пять записей изменений (включая сам tagDatabase); служебные таблицы Liquibase в public остаются пустыми. Повторный накат восстанавливает схему; последующий update ничего не дублирует. Это проверено отдельными Maven-процессами на PostgreSQL 17.11. Интеграционный тест дополнительно сравнивает полную структуру до и после отката, включая защищённую историю.

Все способы запуска используют один logicalFilePath и служебную схему public. Это предотвращает появление второй истории, когда имя пользователя БД совпадает с бизнес-схемой kkd. Применённые миграции в дальнейшем нужно расширять новыми changeset.

## Архитектура и проверенные сценарии

Контроллеры передают запросы прикладным сервисам; правила и формулы работают в чистом доменном слое. JDBC хранит и читает снимки PostgreSQL. Завершённые прогоны защищены от изменения, поэтому история не зависит от текущих целей и иерархии. Подробности транзакций и схемы — в [дизайне](specs/design.md).

| Каталог | Содержимое |
| --- | --- |
| backend/src/main/java/ru/kkd/api | HTTP, DTO, проверка параметров, ошибки |
| backend/src/main/java/ru/kkd/application | Прогоны, демо, метрики и запросы |
| backend/src/main/java/ru/kkd/domain | Модели, четыре правила, формулы и дельта |
| backend/src/main/java/ru/kkd/persistence | JDBC-запросы и сохранение снимков |
| backend/src/main/resources/db/changelog | Накат и обратные SQL-скрипты |
| specs/ | Требования, критерии приёмки и решения при работе с ИИ |

Проверены все правила и границы 45 дней, формулы и округление, первый/пустой прогон, фильтры/пагинация и ошибки API, неизменность истории, блокировки и откат частичного прогона. На PostgreSQL проверен цикл накат → откат → повторный накат. Контейнерные проверки покрывают старт с пустой БД, сохранение данных после down/up, отсутствие дублей демо, новый прогон и восстановление после отказа БД. Полный протокол — в [docs/progress.md](docs/progress.md).

## Реализованные правила

Все правила работают только для активных целей и их КР.

| Код | Условие | Важность |
| --- | --- | --- |
| GOAL_NO_OWNER | Нет ответственного: null, пустая или пробельная строка | critical |
| GOAL_NO_KR | Нет ни одного КР | critical |
| KR_WEIGHTS_SUM | КР есть, сумма весов численно отличается от 100 | major |
| KR_STALE_PROGRESS | Нет даты обновления факта либо прошло больше 45 календарных дней до даты снимка | minor |

Цель без КР не получает дополнительную проблему суммы весов. Ровно 45 дней допустимо; будущая дата не устаревшая. Вес считается через BigDecimal без округления; диапазон отдельного веса выбранными правилами не проверяется. Проблема КР содержит ID связанной цели и подразделения.

DataQualityChecker — обычный Java-компонент без Spring, SQL и обращения к системным часам. Некорректный вход отклоняется до выполнения правил через IllegalArgumentException, без частичного результата. Проверка циклов и SQL-функция потомков реализованы в БД; агрегация метрик использует эти исторические иерархии.

## Готовность приложения и CI

Actuator версии текущего Spring Boot открывает только health endpoint-ы, без компонентов и подробностей БД:

```sh
curl -i http://localhost:8080/actuator/health/readiness
curl -i http://localhost:8080/actuator/health/liveness
```

Readiness возвращает 200 и {"status":"UP"} после полного запуска, включая миграции и демо. При недоступности БД — 503 и {"status":"DOWN"}; во время отказа принимать трафик — 503 и OUT_OF_SERVICE. Liveness отражает состояние процесса и не зависит от БД. Ответы этих служебных endpoint-ов используют формат Actuator, отдельно от error.code/message прикладного API. Остальные Actuator endpoint-ы и список ссылок /actuator закрыты (404).

Образ собирается в два этапа: JDK 21 и Maven Wrapper для сборки, JRE 21 для запуска. Образы Java закреплены digest; при обновлении их нужно менять явно. Приложение работает под UID/GID 10001, с файловой системой только для чтения и временным /tmp. Пароли, Git и локальные кэши не попадают в контекст сборки.

[GitHub Actions](.github/workflows/ci.yml) запускает полный verify и проверку контейнерного развёртывания на push/PR в main и вручную. Actions закреплены полными SHA; права — contents:read. Отчёты тестов и успешный JAR сохраняются на 7 дней. Сборка Docker пропускает выполнение тестов внутри контейнера: полный набор уже выполняется отдельным шагом CI.

Проверку развёртывания можно повторить из корня (нужны Docker Compose и Python 3):

```sh
python3 scripts/check_compose.py
```

Она собирает образ, создаёт отдельный проект со случайными портами и паролем, проверяет HTTP API, демо, права контейнера, повторный старт приложения и отказ/восстановление БД. В конце удаляет только собственные контейнеры и том; существующий проект и его данные не использует. При ошибке выводит последние логи.

## Границы проверки

Согласованная backend-спецификация сверена с реализацией и локальными проверками. Чистая копия исходников из Git запускается по README на Linux с новым томом БД. Для коммита 5afaace подтверждён [успешный запуск GitHub Actions](https://github.com/wow-vulpes/InternSberBackend/actions/runs/41178861616): verify, контейнерная проверка и загрузка артефактов. Windows отдельно не проверен.

Доступ к Storybook, существующим корпоративным сервисам и ИФТ не предоставлен. Локальные проверки не подтверждают корпоративную интеграцию или развёртывание на ИФТ.
