# Дизайн решения

Документ описывает согласованное направление; наличие раздела не означает готовность функции. Каркас шага 1 реализован, проверен и принят пользователем; создание первого коммита разрешено.

## Архитектура

Одно Spring Boot приложение, один Maven-модуль backend/, PostgreSQL. Frontend исключён из объёма. В дальнейшем пакеты ru.kkd.domain (модель и чистые расчёты), application (сценарии и транзакции), persistence (SQL), api (HTTP и валидация). API вызывает прикладные сервисы; бизнес-правила не зависят от контроллеров и SQL.

Решение JDBC вместо JPA: явные SQL-запросы для иерархии, снимков и агрегатов; ORM не нужен для небольшого проекта. Liquibase выбран для явных rollback-скриптов и проверки цикла миграций. Очереди, кеши и отдельные микросервисы не требуются.

## Текущий каркас

- Java 21, Spring Boot 3.5.16, Maven Wrapper с Maven 3.9.11.
- Spring Web, Validation и Spring Boot Test. Версии управляются parent POM Spring Boot.
- ru.kkd.KkdApplication.main(String[] args) запускает контекст и встроенный HTTP-сервер.
- application.yml задаёт spring.application.name=kkd-service и server.port=${SERVER_PORT:8080}.
- БД, контроллеров и заглушек бизнес-функций нет; запуск не требует PostgreSQL.
- .env.example — пример переменных, а не автоматически загружаемый Spring Boot файл.
- KkdApplicationTest.contextLoads загружает Spring-контекст без HTTP-сервера и БД; бизнес-поведение не проверяет.
- Maven Enforcer 3.6.2 на фазе validate разрешает только JDK 21 (диапазон [21,22)) с подсказкой настроить JAVA_HOME.
- Spotless 3.0.0 на фазе validate проверяет Java-исходники и тесты: Google Java Format 1.28.0, стиль AOSP, без завершающих пробелов и с переводом строки в конце. Обычная сборка не исправляет файлы автоматически; для этого есть spotless:apply.

## Статус проверки каркаса

В Linux на JDK 21 выполнены компиляция, тест загрузки контекста и полный цикл verify (1 тест без ошибок и пропусков). Проверено, что validate отклоняет JDK 18 и нарушение форматирования; исходники после отрицательной проверки восстановлены.

Проверены исполняемый JAR (порт 8080) и spring-boot:run с SERVER_PORT=8081. GET /api/runs в обоих случаях возвращает стандартный 404, поскольку бизнес-API ещё нет. Оба процесса остановлены. Это проверки каркаса, а не приёмка функций ККД.

Windows и чистое окружение пока не проверены. Подробности фактических проверок и разрешённый следующий переход — в docs/progress.md.

## Планируемая модель данных

- Подразделение: стабильный ID, название, родительское подразделение.
- Цель: стабильный ID, подразделение, ответственный, родительская цель, статус, срок.
- КР: стабильный ID, цель, целевое/фактическое значение, вес, дата обновления факта.
- Правило: код, название, важность.
- Прогон: ID, дата снимка, статус, сравниваемый прогон; детали выполнения уточнить на шаге 4.
- Снимки подразделений/целей/КР привязаны к прогону; сохраняют историю и стабильные ID объектов.
- Проблема: прогон, правило, тип/ID объекта, связанная цель и подразделение снимка.

Конкретные таблицы, типы, ключи, индексы, SQL-функция и представление проектируются на шаге 3. Рабочая версия PostgreSQL — 17.11. Планируемый Liquibase — 4.31.1 (из BOM Boot); зависимости добавляются на шаге 3.

## Планируемый процесс

Получить согласованный снимок → применить правила Java-компонентом → сохранить снимок и нарушения → отметить прогон завершённым. Транзакции, сбои и конкуренция уточняются до реализации. Демоданные должны проходить тот же механизм расчёта, что и обычный прогон.

Метрики и дельта строятся по неизменяемым результатам и снимкам. Состав выбранного подразделения вычисляется вместе с потомками в соответствующем снимке. Формулы и идентичность проблем определены в requirements.md.

## Планируемый API

- GET /api/runs: ID, статус, дата снимка, ссылка на сравниваемый прогон, число проблем.
- GET /api/kkd/summary?run_id=&unit_id=: run, compared_to, unit, metrics, issues_by_severity, delta по БТ.
- GET /api/kkd/issues: run_id, фильтры unit_id/rule/severity, пагинация limit/offset/total; точные имена и обязательность параметров согласовать на шаге 6.
- Неизвестные прогон/подразделение — 404; некорректные параметры — 422; единая оболочка error с code/message.

Полные DTO, ошибки, сортировка, ограничения и примеры будут описаны до реализации API. До шага 6 бизнес-API не считается доступным. Команду запуска прогонов проектируем отдельно на шаге 4; публичный POST заранее не обещается.

## Проверки и запуск

JUnit 5 для правил, метрик и дельты; Testcontainers с PostgreSQL для SQL и миграций; проверки HTTP-контрактов на шаге API. В конечном решении docker compose up запускает PostgreSQL и приложение, включая миграции и демоданные. Сейчас Compose отсутствует.
