# Дизайн решения

Реализация требований из [requirements.md](requirements.md). Команды запуска, тестов и отката приведены в [README](../README.md).

## Архитектура и основные решения

Один Spring Boot сервис и PostgreSQL. Пакет api отвечает за HTTP, DTO и проверку параметров; application — за сценарии и транзакции; domain — за модели, правила и формулы; persistence — за SQL. Контроллеры вызывают прикладные сервисы. Четыре правила собраны в чистом DataQualityChecker, который принимает данные и дату снимка и возвращает список проблем. Пустые ID, null вместо обязательных значений и дубли объектов отклоняются без частичного результата.

| Решение | Причина | Ограничение |
| --- | --- | --- |
| JDBC и явные SQL-запросы | Запросы к иерархии, снимкам и агрегатам видны непосредственно в коде | Преобразование строк БД в модели поддерживается вручную |
| Снимки источников для каждого прогона | Старые отчёты воспроизводимы после изменения данных и иерархии | Растут объём хранения и стоимость создания прогона |
| Чистые правила и калькулятор метрик | Граничные случаи проверяются без Spring и БД | Приложение загружает данные выбранного снимка в память |
| Транзакция, общая блокировка прогонов и блокировка источников | Параллельные прогоны упорядочены, снимок соответствует согласованному состоянию источников | Изменения источников ожидают завершения прогона |
| Liquibase и защита истории в БД | Схема воспроизводима; ограничения действуют и при прямом SQL | Откат удаляет бизнес-схему с данными и требует остановленного приложения |

## Модель данных

Бизнес-схема kkd содержит девять таблиц. Служебные таблицы Liquibase находятся в public.

| Таблица | Основные данные |
| --- | --- |
| unit | ID, название, родительское подразделение |
| goal | ID, название, подразделение, ответственный, родительская цель, ACTIVE/INACTIVE, срок |
| key_result | ID, название, цель, целевое/фактическое значение, вес, дата обновления факта |
| kkd_rule | Код, название, важность и тип объекта правила |
| kkd_run | ID, дата снимка, статус, compared_to_id, время начала/окончания, код ошибки |
| unit_snapshot | Подразделения и их иерархия на момент прогона |
| goal_snapshot | Цели и связи на момент прогона |
| key_result_snapshot | КР и их значения на момент прогона |
| kkd_issue | Прогон, правило, сохранённая важность, цель и при необходимости КР |

ID исходных объектов — непустые строки; они сохраняются в снимках. Ключ снимка — (run_id, id), связи между снимками составные и не допускают ссылок на другой прогон. Снимки не ссылаются на изменяемые таблицы источника. Отсутствующие ответственный и дата обновления допустимы как вход для правил; вес обязателен. Числа хранятся в numeric без округления весов, даты и числа должны быть конечными.

Тип и ID объекта проблемы вычисляются из goal_id/key_result_id. Ключ (run_id, rule_code, object_type, object_id) исключает дубли. Внешние ключи проверяют принадлежность КР цели и соответствие важности/типа справочнику правил. Подразделение проблемы определяется через цель снимка.

Триггеры разрешают запись снимков и проблем только для RUNNING и запрещают изменение терминальных прогонов. Блокировка строки прогона упорядочивает запись и завершение. Перед COMPLETED функция validate_snapshot проверяет циклы иерархии подразделений и целей. Административное удаление схемы не входит в защиту от обычных операций записи.

Функция unit_subtree(run_id, unit_id) рекурсивно возвращает подразделение с потомками. VIEW run_statistics показывает глобальное число проблем и счётчики важности; для RUNNING/FAILED они равны null. Качество целей и дельта рассчитываются в Java.

## Выполнение прогона

RunService выполняет одну транзакцию READ COMMITTED:

1. Получает транзакционную advisory-блокировку, общую с инициализацией демо.
2. Выбирает COMPLETED с snapshot_date не позже текущей, порядок finished_at DESC, id DESC. Создаёт RUNNING с новым UUID и сохранённым compared_to_id.
3. Создаёт savepoint, берёт SHARE-блокировки таблиц unit, goal и key_result, копирует их в снимок и проверяет отсутствие циклов. Обычное чтение источников остаётся доступным.
4. Выполняет правила по снимку, сохраняет проблемы и завершает прогон как COMPLETED.
5. При ошибке захвата/расчёта/сохранения откатывает частичные данные к savepoint и сохраняет FAILED с RUN_EXECUTION_FAILED.

Ожидание блокировки ограничено 10 секундами, отдельная SQL-команда — 60 секундами. Сбой до создания строки или при commit может откатить весь прогон без сохранённого FAILED. Другие соединения видят результат только после commit; при аварийном завершении процесса частичный снимок не публикуется.

### Демо и команды

Демо создаёт 24 цели (23 активные), 3 вложенных подразделения U1 → U2 → U3 и два прогона: demo-2026-10-19 и demo-2026-10-26. Правила вычисляют 10 и 8 проблем соответственно. Оба прогона создаются в одной внешней транзакции; ошибка второго откатывает весь набор.

Инициализация принимает пустую БД либо готовую демопару с ожидаемыми датами и ссылкой сравнения. Повторный старт использует эту пару, не переписывает источники и не удаляет дополнительные прогоны. Проверка и создание защищены общей блокировкой.

Режимы kkd.demo.enabled и kkd.run.enabled взаимоисключающие. При локальном Java-старте оба выключены; Compose включает демо через отдельный COMPOSE_DEMO_ENABLED. Одиночный прогон принимает kkd.run.date в формате YYYY-MM-DD, по умолчанию — сегодня UTC. Команда без HTTP завершает процесс после выполнения; FAILED даёт ненулевой код выхода.

## Метрики и сравнение

SummaryService читает сохранённые снимки завершённых прогонов; правила повторно не запускаются. QualityMetricsCalculator считает формулы из [требований](requirements.md#метрики-и-сравнение). Входные коллекции копируются, неизвестная цель проблемы и повторная идентичность отклоняются.

Текущая и прошлая области выбираются по иерархии каждого снимка независимо. Сравнение использует сохранённый compared_to_id, поэтому новые прогоны не меняют старую сводку. Если прошлый прогон существует, но выбранного подразделения в нём нет, предыдущая область пуста. Это отличается от отсутствия самого сравнения.

Расчёты используют BigDecimal. Для каждой метрики delta вычитается из показанных значений; направление улучшения задаётся отдельно для доли и счётчиков. Идентичности проблем сравниваются как множества: new = current ∖ previous, persisting = current ∩ previous, resolved = previous ∖ current. Важность берётся из сохранённой проблемы.

## REST API

Endpoint-ы доступны только для чтения. JSON использует snake_case, числа передаются числами, null-поля сохраняются. Дата — YYYY-MM-DD, время — ISO 8601 со смещением. Коды правил имеют верхний регистр, остальные перечисления — нижний. ID не обрезаются и не преобразуются в UUID.

### GET /api/runs

Параметров нет. Ответ — массив прогонов, порядок started_at DESC, id DESC. Поля элемента: id, snapshot_date, status, compared_to_id, started_at, finished_at, issues_count, error_code. Status — running/completed/failed. Счётчик проблем глобальный, определён только для completed; finished_at равен null только у running, error_code заполнен только у failed. Пустой список — []. Пагинация списка прогонов не предусмотрена.

### GET /api/kkd/summary

Обязательные параметры: run_id и unit_id. Сводка содержит run и compared_to с полями {id,snapshot_date}, unit из текущего снимка, metrics, issues_by_severity и delta.

Метрики идут в порядке clean_goals_share, affected_goals_count, issues_count. Поля: {key,title,unit,value,previous,delta,trend,severity}. Единицы — % для доли и шт. для счётчиков. Trend — better/worse/unchanged либо null. Severity метрики и unit.parent_id — дополнительные поля к фрагменту БТ.

issues_by_severity — массив critical, major, minor, каждый элемент содержит {code,current,previous,delta}. При первом прогоне previous/delta равны null у каждой важности и метрики; compared_to и тренды также null. Верхняя delta содержит new/persisting/resolved, у первого прогона все три значения null.

Пример для второго демопрогона и U1:

```json
{
  "run": {"id": "demo-2026-10-26", "snapshot_date": "2026-10-26"},
  "compared_to": {"id": "demo-2026-10-19", "snapshot_date": "2026-10-19"},
  "unit": {"id": "U1", "name": "Банк", "parent_id": null},
  "metrics": [
    {"key": "clean_goals_share", "title": "Доля корректных целей", "unit": "%", "value": 65.2, "previous": 65.2, "delta": 0.0, "trend": "unchanged", "severity": "critical"},
    {"key": "affected_goals_count", "title": "Цели с проблемами", "unit": "шт.", "value": 8, "previous": 8, "delta": 0, "trend": "unchanged", "severity": "critical"},
    {"key": "issues_count", "title": "Проблемы", "unit": "шт.", "value": 8, "previous": 10, "delta": -2, "trend": "better", "severity": "critical"}
  ],
  "issues_by_severity": [
    {"code": "critical", "current": 3, "previous": 5, "delta": -2},
    {"code": "major", "current": 2, "previous": 2, "delta": 0},
    {"code": "minor", "current": 3, "previous": 3, "delta": 0}
  ],
  "delta": {"new": 3, "persisting": 5, "resolved": 5}
}
```

### GET /api/kkd/issues

| Параметр | Ограничение |
| --- | --- |
| run_id | Обязательный, существующий completed |
| unit_id | Необязательный; включает потомков из снимка |
| rule | Необязательный; точный код одного из четырёх правил |
| severity | Необязательный; critical/major/minor, регистронезависимо |
| limit | По умолчанию 50, диапазон 1–200 |
| offset | По умолчанию 0, диапазон 0–2147483647 |

Фильтры объединяются через AND. Ответ: {items,total,limit,offset}. Total учитывает фильтры до пагинации. За концом выборки items пуст, total сохраняется. Порядок: goal_id, rule_code, object_type, object_id по возрастанию.

Элемент items содержит run_id, rule_code, rule_title, severity, object_type, object_id, object_title, goal_id, goal_title, unit_id, unit_name. Object_type — goal или key_result. Названия объектов берутся из снимка; rule_title — из текущего справочника правил, его подписи отдельно не версионируются.

### Валидация и ошибки

Неизвестные, повторные, пустые параметры и значения с NUL отклоняются до обращения к сервисам. Limit/offset содержат только десятичные цифры, без знака, пробелов и дробной части, и должны помещаться в int. Неожиданная серверная ошибка не преобразуется в ошибку пользовательского ввода.

Единая форма ошибок прикладного API:

```json
{"error":{"code":"INVALID_PARAMETER","message":"limit must be between 1 and 200"}}
```

| HTTP | error.code | Условие |
| --- | --- | --- |
| 404 | RUN_NOT_FOUND / UNIT_NOT_FOUND | Неизвестный ресурс |
| 404 | NOT_FOUND | Неизвестный маршрут |
| 422 | INVALID_PARAMETER | Некорректные параметры |
| 422 | RUN_NOT_COMPLETED | Запрошены результаты running/failed |
| 405 | METHOD_NOT_ALLOWED | Метод не поддерживается; заголовок Allow сохраняется |
| 406 | NOT_ACCEPTABLE | Accept не допускает JSON |
| 500 | INTERNAL_ERROR | Общее сообщение Internal server error без SQL, паролей и трассировки |

## Миграции и поставка

Liquibase применяет baseline-тег kkd-baseline и четыре SQL changeset с явными обратными скриптами. Служебная схема public и стабильный logicalFilePath одинаковы для приложения, Maven Plugin и тестов. Новые изменения добавляются отдельными changeset.

Откат удаляет бизнес-схему вместе с источниками, снимками и защищённой историей. Служебные таблицы остаются пустыми; повторный накат восстанавливает структуру и четыре правила. Откат выполняется на отдельной БД с остановленным приложением; команды находятся в README.

Dockerfile собирает JAR на JDK 21, запускает его на JRE 21 под UID/GID 10001. Базовые образы Java закреплены digest. В образ не попадают .env, Git и локальные кэши. Compose использует read-only root, временный /tmp и постоянный том PostgreSQL; повторный запуск сохраняет данные. Порты доступны только на localhost.

docker compose up работает без .env: БД/пользователь kkd, пароль kkd_local_example, порты приложения/БД 8080/5432. Это публичные настройки локального демо; .env и переменные окружения позволяют их переопределить. Локальный Java-старт требует экспортировать параметры подключения.

## Готовность и проверки

Actuator открывает только health без компонентов и деталей подключения. Readiness зависит от состояния приложения и БД, liveness — только от приложения. Readiness сообщает готовность только после завершения миграций и команд старта. Docker HEALTHCHECK использует /actuator/health/readiness, Compose --wait ожидает healthy. Health имеет стандартный формат Actuator, отдельно от ошибок прикладного API.

JUnit проверяет чистые правила и формулы. Testcontainers с PostgreSQL проверяет схему, откат, конкурентную запись и сценарии прогонов; MockMvc с PostgreSQL — HTTP-контракты. scripts/check_compose.py собирает образ и проверяет настоящий HTTP, демо, перезапуск и восстановление БД в отдельном проекте с очисткой собственных ресурсов.

GitHub Actions выполняет Maven verify и контейнерную проверку, сохраняет отчёты и JAR на 7 дней. Actions закреплены SHA, права workflow — contents:read. Команды воспроизведения — в README, [покрытие проверками](requirements.md#покрытие-проверками) и их [результаты](requirements.md#результаты-проверки) — в требованиях.

## Ограничения внедрения

Снимки загружаются в память, запись источников блокируется на время прогона. Такое решение подходит для объёма тестового; перед внедрением нужно проверить допустимый объём данных и время блокировок. Применённые блокировки и ограничения не заменяют разграничение прав доступа.

Локальный Compose использует одну учётную запись для миграций и приложения. Корпоративное внедрение требует отдельных ролей с минимальными правами, управления секретами, авторизации и сопоставления реальных источников. Текущая конфигурация не подтверждает готовность к ИФТ.
