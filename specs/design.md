# Дизайн решения

Документ описывает согласованное направление; наличие раздела не означает готовность функции. Шаг 1 завершён и закоммичен (85b503b). Доменная логика шага 2 реализована, прошла общую проверку D и принята пользователем; создание согласованного коммита разрешено.

## Архитектура

Одно Spring Boot приложение, один Maven-модуль backend/, PostgreSQL. Frontend исключён из объёма. В дальнейшем пакеты ru.kkd.domain (модель и чистые расчёты), application (сценарии и транзакции), persistence (SQL), api (HTTP и валидация). API вызывает прикладные сервисы; бизнес-правила не зависят от контроллеров и SQL.

Решение JDBC вместо JPA: явные SQL-запросы для иерархии, снимков и агрегатов; ORM не нужен для небольшого проекта. Liquibase выбран для явных rollback-скриптов и проверки цикла миграций. Очереди, кеши и отдельные микросервисы не требуются.

## Текущий каркас

- Java 21, Spring Boot 3.5.16, Maven Wrapper с Maven 3.9.11.
- Spring Web, Validation и Spring Boot Test. Версии управляются parent POM Spring Boot.
- ru.kkd.KkdApplication.main(String[] args) запускает контекст и встроенный HTTP-сервер.
- application.yml задаёт spring.application.name=kkd-service и server.port=${SERVER_PORT:8080}.
- БД, контроллеров и заглушек бизнес-функций нет; запуск не требует PostgreSQL.
- .env.example — пример переменных, а не автоматически загружаемый Spring Boot файл.
- KkdApplicationTest.contextLoads загружает Spring-контекст без HTTP-сервера и БД; бизнес-поведение не проверяет.
- Maven Enforcer 3.6.2 на фазе validate разрешает только JDK 21 (диапазон [21,22)) с подсказкой настроить JAVA_HOME.
- Spotless 3.0.0 на фазе validate проверяет Java-исходники и тесты: Google Java Format 1.28.0, стиль AOSP, без завершающих пробелов и с переводом строки в конце. Обычная сборка не исправляет файлы автоматически; для этого есть spotless:apply.

## Проверки каркаса на шаге 1

В Linux на JDK 21 выполнены компиляция, тест загрузки контекста и полный цикл verify (1 тест без ошибок и пропусков). Проверено, что validate отклоняет JDK 18 и нарушение форматирования; исходники после отрицательной проверки восстановлены.

Проверены исполняемый JAR (порт 8080) и spring-boot:run с SERVER_PORT=8081. GET /api/runs в обоих случаях возвращает стандартный 404, поскольку бизнес-API ещё нет. Оба процесса остановлены. Это проверки каркаса, а не приёмка функций ККД.

Windows и чистое окружение пока не проверены. Подробности фактических проверок и разрешённый следующий переход — в docs/progress.md.

## Модель данных

### Доменная модель шага 2

Согласованный дизайн: один Java-компонент ru.kkd.domain.rule.DataQualityChecker, без Spring, SQL, интерфейса и отдельного класса на каждое правило. Проверки выделены в методы внутри компонента.

Созданы типы в ru.kkd.domain.model:

- GoalSnapshot(String id, String unitId, String owner, boolean active, List<KeyResultSnapshot> keyResults). ID обязательны; null-список и null-элементы отклоняются, затем список копируется через List.copyOf.
- KeyResultSnapshot(String id, BigDecimal weight, LocalDate progressUpdatedOn).
- RuleCode: GOAL_NO_OWNER/GOAL_NO_KR → CRITICAL, KR_WEIGHTS_SUM → MAJOR, KR_STALE_PROGRESS → MINOR.
- Severity: CRITICAL, MAJOR, MINOR; ObjectType: GOAL, KEY_RESULT.
- Issue(RuleCode ruleCode, ObjectType objectType, String objectId, String goalId, String unitId). severity() определяется кодом правила, без дублирования хранимой важности.

Основной контракт: `List<Issue> check(List<GoalSnapshot> goals, LocalDate snapshotDate)`.

**Текущий статус C.2:** модели валидируют обязательные поля через IllegalArgumentException. KeyResultSnapshot требует ID и вес; owner и progressUpdatedOn могут отсутствовать. Issue требует код правила, тип и все ID. Общие проверки ID/null вынесены в закрытый для других пакетов ModelValidation, чтобы обеспечить единый контракт ошибок без копирования проверок в трёх моделях. Значения ID не обрезаются и не нормализуются; тип boolean не допускает null для активности.

DataQualityChecker.check проверяет наличие списка целей, даты снимка, элементов и уникальность ID целей и КР во всём наборе, включая неактивные цели. Для каждого типа используется отдельное множество ID, поэтому ID цели и КР могут совпадать. Список вызывающего кода не изменяется. Дубли КР внутри одной цели также отклоняются на уровне check.

После успешной валидации check выполняет четыре правила для активных целей. Каждое правило выделено в отдельный private-метод; в компоненте нет изменяемого состояния между вызовами. Результат сортируется и копируется через List.copyOf. Заглушка удалена; три временных сценария заменены проверками конкретных проблем, включая пустой набор и совпадающие ID цели/КР. Компонент не подключён к Spring и не доступен через API.

### Реализованное поведение

- GOAL_NO_OWNER: null, пустой или пробельный owner → одна проблема цели.
- GOAL_NO_KR: пустой список КР → одна проблема цели; KR_WEIGHTS_SUM в этом случае не создаётся.
- KR_WEIGHTS_SUM: при наличии КР сумма BigDecimal численно отличается от 100 → одна проблема цели; различия масштаба не важны, округления нет.
- KR_STALE_PROGRESS: progressUpdatedOn отсутствует либо прошло более 45 дней до snapshotDate → проблема конкретного КР со связанной целью и подразделением. Ровно 45 дней допустимо; будущая дата не устаревшая. Используется ChronoUnit.DAYS.between, эквивалентный сравнению с snapshotDate.minusDays(45) на обычных датах и безопасный на границах LocalDate.MIN/MAX.
- Правила пропускают неактивные цели и их КР. Корректность входной структуры проверяется до выполнения правил; некорректный набор не даёт частичного результата.
- Неизменяемый результат сортируется по goalId, имени ruleCode, имени objectType, objectId. Каждый вызов использует переданную дату снимка, без системных часов и изменения входных данных.

В C.1 добавлены GoalSnapshotTest, KeyResultSnapshotTest, IssueTest и DataQualityCheckerTest: обязательные поля, null/пустые/пробельные ID, дубли, сохранение отсутствующих owner/даты, отсутствие проверки диапазона и округления веса, защитное копирование списка, важность правил. В C.2 временные проверки недоступности расчёта в DataQualityCheckerTest заменены проверками результата. Тесты не используют Spring/БД/моки.

В C.2 добавлен DataQualityRulesTest (42 сценария) для REQ-01, BR-01–05 и BR-13: отсутствие ответственного, пустые/непустые КР, сумма 100 с разным масштабом и отклонения 99.99/100.01, точные дробные веса, 44/45/46 дней, null/будущая дата, границы месяца/года, високосный год и пределы LocalDate, неактивные цели, несколько проблем, связи объектов, неизменяемость результата и повторяемость. На D полный verify успешно выполнил все 100 сценариев (99 доменных и 1 тест контекста). В исполняемом JAR проверено наличие всех восьми доменных типов. Проверки D не потребовали изменения Java-кода или зависимостей; после отчёта пользователь принял шаг 2.

Подэтапы: B — каркас и компиляция; C.1 — модели/валидация и их тесты; C.2 — все четыре правила и бизнес-тесты; D — общая проверка; E/F — подготовка и отдельное разрешение на коммит. Новых зависимостей, БД и HTTP в шаге 2 нет.

### Будущая схема хранения

- Подразделение: стабильный ID, название, родительское подразделение.
- Цель: стабильный ID, подразделение, ответственный, родительская цель, статус, срок.
- КР: стабильный ID, цель, целевое/фактическое значение, вес, дата обновления факта.
- Правило: код, название, важность.
- Прогон: ID, дата снимка, статус, сравниваемый прогон; детали выполнения уточнить на шаге 4.
- Снимки подразделений/целей/КР привязаны к прогону; сохраняют историю и стабильные ID объектов.
- Проблема: прогон, правило, тип/ID объекта, связанная цель и подразделение снимка.

Конкретные таблицы, типы, ключи, индексы, SQL-функция и представление проектируются на шаге 3. Рабочая версия PostgreSQL — 17.11. Планируемый Liquibase — 4.31.1 (из BOM Boot); зависимости добавляются на шаге 3.

## Планируемый процесс

Получить согласованный снимок → применить правила Java-компонентом → сохранить снимок и нарушения → отметить прогон завершённым. Транзакции, сбои и конкуренция уточняются до реализации. Демоданные должны проходить тот же механизм расчёта, что и обычный прогон.

Метрики и дельта строятся по неизменяемым результатам и снимкам. Состав выбранного подразделения вычисляется вместе с потомками в соответствующем снимке. Формулы и идентичность проблем определены в requirements.md.

## Планируемый API

- GET /api/runs: ID, статус, дата снимка, ссылка на сравниваемый прогон, число проблем.
- GET /api/kkd/summary?run_id=&unit_id=: run, compared_to, unit, metrics, issues_by_severity, delta по БТ.
- GET /api/kkd/issues: run_id, фильтры unit_id/rule/severity, пагинация limit/offset/total; точные имена и обязательность параметров согласовать на шаге 6.
- Неизвестные прогон/подразделение — 404; некорректные параметры — 422; единая оболочка error с code/message.

Полные DTO, ошибки, сортировка, ограничения и примеры будут описаны до реализации API. До шага 6 бизнес-API не считается доступным. Команду запуска прогонов проектируем отдельно на шаге 4; публичный POST заранее не обещается.

## Проверки и запуск

JUnit 5 для правил, метрик и дельты; Testcontainers с PostgreSQL для SQL и миграций; проверки HTTP-контрактов на шаге API. В конечном решении docker compose up запускает PostgreSQL и приложение, включая миграции и демоданные. Сейчас Compose отсутствует.
