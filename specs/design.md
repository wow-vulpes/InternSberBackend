# Дизайн решения

Спецификация реализации, подготовленная и обновляемая при работе с ИИ-ассистентом. Описывает модель данных, контракты и причины ключевых решений. Реализованы доменные правила и хранение в PostgreSQL; процесс выполнения прогонов, метрики/дельта и REST API пока запланированы. Требования и критерии приёмки — в [requirements.md](requirements.md).

## Архитектура

Одно Spring Boot приложение, один Maven-модуль backend/, PostgreSQL. Frontend исключён из объёма. В дальнейшем пакеты ru.kkd.domain (модель и чистые расчёты), application (сценарии и транзакции), persistence (SQL), api (HTTP и валидация). API вызывает прикладные сервисы; бизнес-правила не зависят от контроллеров и SQL.

Решение JDBC вместо JPA: явные SQL-запросы для иерархии, снимков и агрегатов; ORM не нужен для небольшого проекта. Liquibase выбран для явных rollback-скриптов и проверки цикла миграций. Очереди, кеши и отдельные микросервисы не требуются.

## Текущий каркас

- Java 21, Spring Boot 3.5.16, Maven Wrapper с Maven 3.9.11.
- Spring Web, Validation, JDBC, Liquibase 4.31.1, PostgreSQL JDBC 42.7.11 и Spring Boot Test; Testcontainers 1.21.4. Версии зависимостей управляются parent POM Spring Boot.
- ru.kkd.KkdApplication.main(String[] args) запускает контекст и встроенный HTTP-сервер.
- application.yml задаёт spring.application.name=kkd-service и server.port=${SERVER_PORT:8080}.
- При запуске требуется PostgreSQL; Liquibase автоматически применяет миграции. Бизнес-контроллеров и заглушек будущих функций нет.
- .env.example — пример переменных, а не автоматически загружаемый Spring Boot файл.
- KkdApplicationTest.contextLoads загружает Spring-контекст без HTTP-сервера с временной PostgreSQL; проверяет автоматический накат и четыре записи справочника.
- Maven Enforcer 3.6.2 на фазе validate разрешает только JDK 21 (диапазон [21,22)) с подсказкой настроить JAVA_HOME.
- Spotless 3.0.0 на фазе validate проверяет Java-исходники и тесты: Google Java Format 1.28.0, стиль AOSP, без завершающих пробелов и с переводом строки в конце. Обычная сборка не исправляет файлы автоматически; для этого есть spotless:apply.

## Модель данных

### Доменная модель

Один Java-компонент ru.kkd.domain.rule.DataQualityChecker, без Spring, SQL, интерфейса и отдельного класса на каждое правило. Проверки выделены в методы внутри компонента.

Созданы типы в ru.kkd.domain.model:

- GoalSnapshot(String id, String unitId, String owner, boolean active, List<KeyResultSnapshot> keyResults). ID обязательны; null-список и null-элементы отклоняются, затем список копируется через List.copyOf.
- KeyResultSnapshot(String id, BigDecimal weight, LocalDate progressUpdatedOn).
- RuleCode: GOAL_NO_OWNER/GOAL_NO_KR → CRITICAL, KR_WEIGHTS_SUM → MAJOR, KR_STALE_PROGRESS → MINOR.
- Severity: CRITICAL, MAJOR, MINOR; ObjectType: GOAL, KEY_RESULT.
- Issue(RuleCode ruleCode, ObjectType objectType, String objectId, String goalId, String unitId). severity() определяется кодом правила, без дублирования хранимой важности.

Основной контракт: `List<Issue> check(List<GoalSnapshot> goals, LocalDate snapshotDate)`.

Модели валидируют обязательные поля через IllegalArgumentException. KeyResultSnapshot требует ID и вес; owner и progressUpdatedOn могут отсутствовать. Issue требует код правила, тип и все ID. Общие проверки ID/null вынесены в закрытый для других пакетов ModelValidation, чтобы обеспечить единый контракт ошибок без копирования проверок в трёх моделях. Значения ID не обрезаются и не нормализуются; тип boolean не допускает null для активности.

DataQualityChecker.check проверяет наличие списка целей, даты снимка, элементов и уникальность ID целей и КР во всём наборе, включая неактивные цели. Для каждого типа используется отдельное множество ID, поэтому ID цели и КР могут совпадать. Список вызывающего кода не изменяется. Дубли КР внутри одной цели также отклоняются на уровне check.

После успешной валидации check выполняет четыре правила для активных целей. Каждое правило выделено в отдельный private-метод; в компоненте нет изменяемого состояния между вызовами. Результат сортируется и копируется через List.copyOf. Компонент не подключён к Spring и не доступен через API.

### Реализованное поведение

- GOAL_NO_OWNER: null, пустой или пробельный owner → одна проблема цели.
- GOAL_NO_KR: пустой список КР → одна проблема цели; KR_WEIGHTS_SUM в этом случае не создаётся.
- KR_WEIGHTS_SUM: при наличии КР сумма BigDecimal численно отличается от 100 → одна проблема цели; различия масштаба не важны, округления нет.
- KR_STALE_PROGRESS: progressUpdatedOn отсутствует либо прошло более 45 дней до snapshotDate → проблема конкретного КР со связанной целью и подразделением. Ровно 45 дней допустимо; будущая дата не устаревшая. Используется ChronoUnit.DAYS.between, эквивалентный сравнению с snapshotDate.minusDays(45) на обычных датах и безопасный на границах LocalDate.MIN/MAX.
- Правила пропускают неактивные цели и их КР. Корректность входной структуры проверяется до выполнения правил; некорректный набор не даёт частичного результата.
- Неизменяемый результат сортируется по goalId, имени ruleCode, имени objectType, objectId. Каждый вызов использует переданную дату снимка, без системных часов и изменения входных данных.

Доменные тесты проверяют обязательные поля, дубли ID, неизменяемость, все четыре правила, точность весов, границы 45 дней, будущие даты, пределы LocalDate, неактивные цели и повторяемость результата. Доменный слой не использует Spring, SQL и моки.

### Схема хранения

PostgreSQL 17.11. Бизнес-схема `kkd` содержит девять таблиц:

| Таблица | Назначение |
| --- | --- |
| unit | Текущее подразделение: ID, название, родитель |
| goal | Текущая цель: ID, подразделение, родительская цель, ответственный, статус ACTIVE/INACTIVE, срок |
| key_result | Текущий КР: ID, цель, вес, цель/факт и дата обновления |
| kkd_run | Прогон: ID, дата снимка, статус, сравниваемый прогон, время начала/завершения, ошибка |
| unit_snapshot | Иерархия подразделений конкретного прогона |
| goal_snapshot | Цели и их связи в конкретном прогоне |
| key_result_snapshot | КР и их связи в конкретном прогоне |
| kkd_rule | Справочник четырёх правил: код, название, важность, тип объекта |
| kkd_issue | Проблемы с правилом, сохранённой важностью, целью и при необходимости КР |

ID исходных объектов — непустой text; ID сохраняются в снимках. Ключ снимка `(run_id,id)`, связи внутри снимка составные. Снимки не ссылаются на изменяемые исходные таблицы, поэтому изменения/удаление источника не меняют историю. Названия и обязательные ссылки защищены CHECK/FK. owner, срок, целевое/фактическое значение и дата обновления могут отсутствовать. Вес обязателен, хранится как numeric без заданного масштаба; NaN и бесконечности отклоняются. Веса не округляются и не ограничиваются диапазоном 0–100: проверяется сумма правилом Java. Даты/время должны быть конечными; время — timestamptz.

У проблемы тип и ID объекта вычисляются из goal_id/key_result_id (generated columns). Ключ `(run_id,rule_code,object_type,object_id)` предотвращает дубли. Составные FK проверяют принадлежность КР цели и соответствие правила важности/типу объекта. Подразделение определяется через цель снимка.

Новый прогон создаётся только RUNNING. Дата, ID, ссылка сравнения и время начала после создания неизменяемы. Допустим переход в COMPLETED или FAILED; время завершения обязательно, ошибка обязательна только для FAILED. Сравнение допускается только с COMPLETED, дата которого не позже текущей; одинаковые даты допустимы. Выбор предыдущего прогона из Java ещё не реализован.

Триггеры защищают завершённые и неуспешные прогоны, снимки и проблемы от INSERT/UPDATE/DELETE. Запись данных блокирует строку прогона FOR UPDATE и тем самым сериализуется с завершением. Перенос данных между прогонами запрещён. Защита касается обычного DML, а не административных изменений схемы. Прямые ссылки объекта на себя запрещены ограничениями; многоузловые циклы в исходных данных допустимы до проверки снимка, но завершить такой снимок нельзя.

SQL-объекты:

- `validate_snapshot(run_id)` отклоняет циклы подразделений и целей; вызывается при переходе в COMPLETED.
- `guard_run()` и `guard_run_data()` — триггерные функции переходов и неизменяемости.
- `unit_subtree(run_id,unit_id)` — SQL-функция всех потомков вместе с корнем, рекурсивный UNION исключает повторения.
- `run_statistics` — VIEW общего числа проблем и счётчиков critical/major/minor. Для COMPLETED без проблем возвращает 0, для RUNNING/FAILED — null. Метрики качества и дельта ещё не реализованы.

### Миграции и проверки

Корневой XML содержит baseline-тег `kkd-baseline` и четыре SQL-набора с явными обратными скриптами: источники → прогоны/снимки → правила/проблемы → защита/функции/VIEW. Откат выполняется в обратном порядке без CASCADE и удаляет всю бизнес-схему вместе с данными, включая защищённую историю. Liquibase 4.31.1 удаляет также changeset baseline при откате к этому tagDatabase; служебные таблицы остаются, записей истории становится 0. Повторный накат создаёт все объекты и четыре правила заново.

`logicalFilePath=db/changelog/db.changelog-master.xml` стабилизирует идентичность миграций для Spring, Maven Plugin и тестового API. Default schema и служебная schema Liquibase явно заданы как public во всех трёх способах: иначе PostgreSQL после создания kkd может выбрать её по имени пользователя и создать вторую историю. SQL бизнес-объектов всегда квалифицирован схемой kkd. Существующие применённые миграции в дальнейшем не редактировать, добавлять новые changeset.

Проверки на настоящем PostgreSQL через Testcontainers:

- DatabaseSchemaTest: ключи/ссылки, точность numeric, некорректные значения, статусы, циклы, потомки, защита истории и VIEW.
- DatabaseConcurrencyTest: незавершённая запись блокирует завершение; после commit завершение проходит, поздняя запись отклоняется.
- MigrationLifecycleTest: идемпотентный накат, откат заполненной защищённой истории и повторный накат; сравнение таблиц, колонок, ограничений, индексов, функций, триггеров и VIEW. Пользователь БД kkd воспроизводит особенность search_path. Между операциями очищается только процессный FastCheckService cache, имитируя отдельные CLI-процессы.
- KkdApplicationTest: автоматические миграции при загрузке Spring-контекста.

Полный verify: 119 сценариев без ошибок и пропусков. Отдельно проверены Maven update → rollback → update → update и запуск JAR на уже мигрированной БД с неизменной историей. Команды — в README; протокол — в docs/progress.md.

## Планируемый процесс

Получить согласованный снимок → применить правила Java-компонентом → сохранить снимок и нарушения → отметить прогон завершённым. Транзакции, сбои и конкуренция уточняются до реализации. Демоданные должны проходить тот же механизм расчёта, что и обычный прогон.

Метрики и дельта строятся по неизменяемым результатам и снимкам. Состав выбранного подразделения вычисляется вместе с потомками в соответствующем снимке. Формулы и идентичность проблем определены в requirements.md.

## Планируемый API

- GET /api/runs: ID, статус, дата снимка, ссылка на сравниваемый прогон, число проблем.
- GET /api/kkd/summary?run_id=&unit_id=: run, compared_to, unit, metrics, issues_by_severity, delta по БТ.
- GET /api/kkd/issues: run_id, фильтры unit_id/rule/severity, пагинация limit/offset/total; точные имена и обязательность параметров согласовать на шаге 6.
- Неизвестные прогон/подразделение — 404; некорректные параметры — 422; единая оболочка error с code/message.

Полные DTO, ошибки, сортировка, ограничения и примеры будут описаны до реализации API. Бизнес-API пока недоступен. Способ запуска прогонов предстоит определить перед реализацией; публичный POST не предусмотрен текущим контрактом.

## Проверки и запуск

JUnit 5 для правил, метрик и дельты; Testcontainers с PostgreSQL для SQL и миграций; проверки HTTP-контрактов при реализации API. В конечном решении docker compose up запускает PostgreSQL и приложение, включая миграции и демоданные. Сейчас Compose поднимает только PostgreSQL; сервис приложения и демоданные добавляются позже.
