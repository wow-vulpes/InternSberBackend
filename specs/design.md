# Дизайн решения

Спецификация реализации, подготовленная и обновляемая при работе с ИИ-ассистентом. Описывает модель данных, контракты и причины ключевых решений. Реализованы доменные правила, хранение в PostgreSQL, выполнение прогонов, демонстрационные данные, метрики и сравнение прогонов. REST API реализован. Требования и критерии приёмки — в [requirements.md](requirements.md).

## Архитектура

Одно Spring Boot приложение, один Maven-модуль backend/, PostgreSQL. Frontend исключён из объёма. Пакеты ru.kkd.domain (модель и чистые расчёты), application (сценарии и транзакции), persistence (SQL). Пакет api отвечает за HTTP, DTO, преобразование значений и валидацию параметров. API вызывает прикладные сервисы; бизнес-правила не зависят от контроллеров и SQL.

Решение JDBC вместо JPA: явные SQL-запросы для иерархии, снимков и агрегатов; ORM не нужен для небольшого проекта. Liquibase выбран для явных rollback-скриптов и проверки цикла миграций. Очереди, кеши и отдельные микросервисы не требуются.

## Модель данных

### Доменная модель

Один Java-компонент ru.kkd.domain.rule.DataQualityChecker, без Spring, SQL, интерфейса и отдельного класса на каждое правило. Проверки выделены в методы внутри компонента.

Созданы типы в ru.kkd.domain.model:

- GoalSnapshot(String id, String unitId, String owner, boolean active, List<KeyResultSnapshot> keyResults). ID обязательны; null-список и null-элементы отклоняются, затем список копируется через List.copyOf.
- KeyResultSnapshot(String id, BigDecimal weight, LocalDate progressUpdatedOn).
- RuleCode: GOAL_NO_OWNER/GOAL_NO_KR → CRITICAL, KR_WEIGHTS_SUM → MAJOR, KR_STALE_PROGRESS → MINOR.
- Severity: CRITICAL, MAJOR, MINOR; ObjectType: GOAL, KEY_RESULT.
- Issue(RuleCode ruleCode, ObjectType objectType, String objectId, String goalId, String unitId). severity() определяется кодом правила, без дублирования хранимой важности.

Основной контракт: `List<Issue> check(List<GoalSnapshot> goals, LocalDate snapshotDate)`.

Модели валидируют обязательные поля через IllegalArgumentException. KeyResultSnapshot требует ID и вес; owner и progressUpdatedOn могут отсутствовать. Issue требует код правила, тип и все ID. Общие проверки ID/null вынесены в закрытый для других пакетов ModelValidation, чтобы обеспечить единый контракт ошибок без копирования проверок в трёх моделях. Значения ID не обрезаются и не нормализуются; тип boolean не допускает null для активности.

DataQualityChecker.check проверяет наличие списка целей, даты снимка, элементов и уникальность ID целей и КР во всём наборе, включая неактивные цели. Для каждого типа используется отдельное множество ID, поэтому ID цели и КР могут совпадать. Список вызывающего кода не изменяется. Дубли КР внутри одной цели также отклоняются на уровне check.

После успешной валидации check выполняет четыре правила для активных целей. Каждое правило выделено в отдельный private-метод; в компоненте нет изменяемого состояния между вызовами. Результат сортируется и копируется через List.copyOf. Чистый компонент зарегистрирован как Spring bean через RunConfiguration и вызывается прикладным сервисом. Результаты доступны через REST API.

### Реализованное поведение

- GOAL_NO_OWNER: null, пустой или пробельный owner → одна проблема цели.
- GOAL_NO_KR: пустой список КР → одна проблема цели; KR_WEIGHTS_SUM в этом случае не создаётся.
- KR_WEIGHTS_SUM: при наличии КР сумма BigDecimal численно отличается от 100 → одна проблема цели; различия масштаба не важны, округления нет.
- KR_STALE_PROGRESS: progressUpdatedOn отсутствует либо прошло более 45 дней до snapshotDate → проблема конкретного КР со связанной целью и подразделением. Ровно 45 дней допустимо; будущая дата не устаревшая. Используется ChronoUnit.DAYS.between, эквивалентный сравнению с snapshotDate.minusDays(45) на обычных датах и безопасный на границах LocalDate.MIN/MAX.
- Правила пропускают неактивные цели и их КР. Корректность входной структуры проверяется до выполнения правил; некорректный набор не даёт частичного результата.
- Неизменяемый результат сортируется по goalId, имени ruleCode, имени objectType, objectId. Каждый вызов использует переданную дату снимка, без системных часов и изменения входных данных.

Доменные тесты проверяют обязательные поля, дубли ID, неизменяемость, все четыре правила, точность весов, границы 45 дней, будущие даты, пределы LocalDate, неактивные цели и повторяемость результата. Доменный слой не использует Spring, SQL и моки.

### Схема хранения

PostgreSQL 17.11. Бизнес-схема `kkd` содержит девять таблиц:

| Таблица | Назначение |
| --- | --- |
| unit | Текущее подразделение: ID, название, родитель |
| goal | Текущая цель: ID, подразделение, родительская цель, ответственный, статус ACTIVE/INACTIVE, срок |
| key_result | Текущий КР: ID, цель, вес, цель/факт и дата обновления |
| kkd_run | Прогон: ID, дата снимка, статус, сравниваемый прогон, время начала/завершения, ошибка |
| unit_snapshot | Иерархия подразделений конкретного прогона |
| goal_snapshot | Цели и их связи в конкретном прогоне |
| key_result_snapshot | КР и их связи в конкретном прогоне |
| kkd_rule | Справочник четырёх правил: код, название, важность, тип объекта |
| kkd_issue | Проблемы с правилом, сохранённой важностью, целью и при необходимости КР |

ID исходных объектов — непустой text; ID сохраняются в снимках. Ключ снимка `(run_id,id)`, связи внутри снимка составные. Снимки не ссылаются на изменяемые исходные таблицы, поэтому изменения/удаление источника не меняют историю. Названия и обязательные ссылки защищены CHECK/FK. owner, срок, целевое/фактическое значение и дата обновления могут отсутствовать. Вес обязателен, хранится как numeric без заданного масштаба; NaN и бесконечности отклоняются. Веса не округляются и не ограничиваются диапазоном 0–100: проверяется сумма правилом Java. Даты/время должны быть конечными; время — timestamptz.

У проблемы тип и ID объекта вычисляются из goal_id/key_result_id (generated columns). Ключ `(run_id,rule_code,object_type,object_id)` предотвращает дубли. Составные FK проверяют принадлежность КР цели и соответствие правила важности/типу объекта. Подразделение определяется через цель снимка.

Новый прогон создаётся только RUNNING. Дата, ID, ссылка сравнения и время начала после создания неизменяемы. Допустим переход в COMPLETED или FAILED; время завершения обязательно, ошибка обязательна только для FAILED. Сравнение допускается только с COMPLETED, дата которого не позже текущей; одинаковые даты допустимы. Предыдущий прогон выбирает RunService через RunRepository, как описано ниже.

Триггеры защищают завершённые и неуспешные прогоны, снимки и проблемы от INSERT/UPDATE/DELETE. Запись данных блокирует строку прогона FOR UPDATE и тем самым сериализуется с завершением. Перенос данных между прогонами запрещён. Защита касается обычного DML, а не административных изменений схемы. Прямые ссылки объекта на себя запрещены ограничениями; многоузловые циклы в исходных данных допустимы до проверки снимка, но завершить такой снимок нельзя.

SQL-объекты:

- `validate_snapshot(run_id)` отклоняет циклы подразделений и целей; вызывается при переходе в COMPLETED.
- `guard_run()` и `guard_run_data()` — триггерные функции переходов и неизменяемости.
- `unit_subtree(run_id,unit_id)` — SQL-функция всех потомков вместе с корнем, рекурсивный UNION исключает повторения.
- `run_statistics` — VIEW общего числа проблем и счётчиков critical/major/minor. Для COMPLETED без проблем возвращает 0, для RUNNING/FAILED — null. Метрики качества и дельта рассчитываются прикладным сервисом отдельно от этого VIEW.

### Миграции и проверки

Корневой XML содержит baseline-тег `kkd-baseline` и четыре SQL-набора с явными обратными скриптами: источники → прогоны/снимки → правила/проблемы → защита/функции/VIEW. Откат выполняется в обратном порядке без CASCADE и удаляет всю бизнес-схему вместе с данными, включая защищённую историю. Liquibase 4.31.1 удаляет также changeset baseline при откате к этому tagDatabase; служебные таблицы остаются, записей истории становится 0. Повторный накат создаёт все объекты и четыре правила заново.

`logicalFilePath=db/changelog/db.changelog-master.xml` стабилизирует идентичность миграций для Spring, Maven Plugin и тестового API. Default schema и служебная schema Liquibase явно заданы как public во всех трёх способах: иначе PostgreSQL после создания kkd может выбрать её по имени пользователя и создать вторую историю. SQL бизнес-объектов всегда квалифицирован схемой kkd. Существующие применённые миграции в дальнейшем не редактировать, добавлять новые changeset.

Проверки на настоящем PostgreSQL через Testcontainers:

- DatabaseSchemaTest: ключи/ссылки, точность numeric, некорректные значения, статусы, циклы, потомки, защита истории и VIEW.
- DatabaseConcurrencyTest: незавершённая запись блокирует завершение; после commit завершение проходит, поздняя запись отклоняется.
- MigrationLifecycleTest: идемпотентный накат, откат заполненной защищённой истории и повторный накат; сравнение таблиц, колонок, ограничений, индексов, функций, триггеров и VIEW. Пользователь БД kkd воспроизводит особенность search_path. Между операциями очищается только процессный FastCheckService cache, имитируя отдельные CLI-процессы.
- KkdApplicationTest: автоматические миграции при загрузке Spring-контекста.

Полный verify текущей реализации: 259 сценариев без ошибок и пропусков. Отдельно проверены Maven update → rollback → update → update и запуск JAR на уже мигрированной БД с неизменной историей. Команды — в [README](../README.md), покрытие и результаты проверки — в [requirements.md](requirements.md#покрытие-проверками).

## Выполнение прогонов

`RunService.run(LocalDate snapshotDate)` создаёт UUID и возвращает неизменяемый `RunResult`: id, snapshotDate, status, comparedToId, issuesCount, errorCode. Для COMPLETED число проблем неотрицательно; для FAILED счётчик null, errorCode=RUN_EXECUTION_FAILED. Null-дата отклоняется до записи в БД. Каждый обычный вызов создаёт отдельный прогон, даже с той же датой и неизменными данными.

Зависимости: RunService → RunRepository и чистый DataQualityChecker. RunConfiguration регистрирует checker и Clock.systemUTC; JDBC-сопоставление выполняет RunRepository. RunResult и RunStatus находятся в domain.model, без зависимости от Spring. Новых библиотек и изменений миграций для выполнения прогонов не требуется.

Алгоритм на `TransactionTemplate` с READ COMMITTED:

1. Получить транзакционную advisory-блокировку `(757001,1)`, общую для обычных прогонов и демо. Она сериализует вызовы приложения в одной БД, в том числе из разных процессов.
2. Выбрать последний по finished_at DESC, id DESC прогон COMPLETED с snapshot_date <= текущей. FAILED и более поздние даты не участвуют. При отсутствии подходящего прогона comparedToId=null. При запуске задним числом история других прогонов не переписывается.
3. Вставить RUNNING и создать savepoint.
4. Взять SHARE-блокировки трёх таблиц источника, скопировать все подразделения, цели и КР в снимок и проверить отсутствие циклов. Блокировки дожидаются текущих писателей и запрещают изменения источника до конца транзакции, обеспечивая согласованность копий на READ COMMITTED. Обычные SELECT не блокируются.
5. Загрузить доменные модели из снимка, выполнить правила, сохранить проблемы и перевести прогон в COMPLETED.
6. При RuntimeException в захвате/расчёте/сохранении откатиться к savepoint, удалить тем самым все частичные результаты и отметить существующую строку FAILED. В лог попадают ID и класс исключения; исходные данные в сообщение не включаются.

Ожидание блокировки ограничено 10 секундами, выполнение SQL-команды — 60 секундами. Ошибка получения общей блокировки, создания строки, фиксации транзакции или недоступность БД передаётся вызывающему коду: сохранение FAILED при таких инфраструктурных сбоях не гарантируется. Приложение не выполняет скрытые повторные попытки.

RUNNING существует внутри открытой транзакции; другим соединениям результат становится виден после commit. Аварийное завершение процесса до commit откатывает весь прогон; частичная история не публикуется. Savepoint позволяет сохранить FAILED при обычной ошибке выполнения, не меняя прежних успешных прогонов. В демо используется одна внешняя транзакция; внутренние вызовы присоединяются к ней.

### Демонстрационные данные

`DemoDataInitializer.initialize()` и `DemoDataRepository` создают набор только при явном включении деморежима. Перед проверкой пустоты берутся общая advisory-блокировка и SHARE ROW EXCLUSIVE-блокировки источников. Если источники или прогоны уже заполнены и завершённой демопары нет, инициализация отклоняется без изменений.

В одной транзакции создаются три подразделения U1 → U2 → U3, 24 цели (по 8 на подразделение, 23 активные и одна неактивная), первое состояние источника, первый прогон, изменения источника и второй прогон. Оба прогона используют тот же RunService и DataQualityChecker, что и обычная команда. При ошибке любого прогона вся инициализация откатывается, включая первый прогон и исходные данные.

| Прогон | Дата снимка | КР | Проблемы | Сравнение |
| --- | --- | --- | --- | --- |
| demo-2026-10-19 | 2026-10-19 | 22 | 10 | null |
| demo-2026-10-26 | 2026-10-26 | 23 | 8 | demo-2026-10-19 |

В первом состоянии присутствуют все четыре правила. Во втором по идентичности `(rule_code,object_type,object_id)` есть 3 новые, 5 сохраняющихся и 5 исправленных проблем. Это проверенные свойства набора данных, используемые тестами расчёта дельты. КР на границе 45 дней демонстрируют изменение при старении данных. Неактивная G24 содержит нарушения, которые правила игнорируют.

Завершённая демопара распознаётся по фиксированным ID, датам, статусам и ссылке сравнения. Повторное включение возвращает ту же пару, сохраняя текущие источники и дополнительные обычные прогоны. Одновременные инициализации сериализуются общей блокировкой.

### Команды запуска

`StartupCommands` — ApplicationRunner. По умолчанию оба режима выключены и запуск приложения не меняет источники и историю. Миграции Liquibase выполняются независимо от этих режимов.

- `kkd.demo.enabled=true` (KKD_DEMO_ENABLED) — инициализировать демо либо использовать готовую пару.
- `kkd.run.enabled=true` (KKD_RUN_ENABLED) — выполнить один новый прогон. Необязательный `kkd.run.date=YYYY-MM-DD` задаёт дату снимка; без параметра используется текущая дата UTC через Clock.
- Одновременное включение режимов отклоняется до изменения данных. Некорректная дата также отклоняется до создания прогона. FAILED приводит к ошибке команды после сохранения статуса.
- Для отдельной команды без HTTP применяется `--spring.main.web-application-type=none`. Для обычного сервера демо можно включить на старте; отдельный запуск прогонов не является HTTP endpoint.

Периодическое расписание не реализовано и не включено. Формулы метрик и идентичность проблем определены в requirements.md.

## Метрики и сравнение прогонов

`SummaryService.summary(String runId, String unitId)` возвращает `QualitySummary`: run, comparedTo, unit, previousUnit и quality (метрики, текущие счётчики важности и дельта проблем). Это прикладной результат; HTTP DTO и сериализация описаны в разделе REST API. RunResult содержит общие сведения о прогоне и глобальное число проблем, а метрики в quality относятся только к выбранному подразделению с потомками.

Сервис проверяет обязательность ID, существование прогона и его статус COMPLETED, затем подразделение в текущем снимке. Пустые/null ID отклоняются через IllegalArgumentException; неизвестный ресурс — ResourceNotFoundException; RUNNING/FAILED — RunNotCompletedException. HTTP-коды и оболочка ошибок подключены в ApiExceptionHandler.

SummaryRepository читает только сохранённые снимки и проблемы. Состав выбранного подразделения определяет `kkd.unit_subtree(runId,unitId)`; цели фильтруются по ACTIVE, проблемы связываются с ними через goal_snapshot. Текущие источники, системная дата и повторный запуск правил в чтении не участвуют. Важность берётся из сохранённого kkd_issue.severity, а не пересчитывается по текущему справочнику. Завершённые снимки неизменяемы, поэтому последовательные SELECT не требуют блокировки источников.

Для сравнения берётся только сохранённый run.comparedToId; появление более новых прогонов не меняет старый отчёт. Подразделение с тем же ID и его потомки выбираются независимо в прошлом снимке. Если подразделения раньше не существовало, previousUnit=null и предыдущая область пуста: счётчики 0, доля null. Это отличается от отсутствия самого прогона сравнения, когда previous/delta/trend и все счётчики изменений равны null.

### Формулы и округление

`QualityMetricsCalculator` — чистый Java-компонент без Spring, SQL и часов, зарегистрированный bean через конфигурацию. Вход `QualitySnapshot` содержит множество ID активных целей и список SnapshotIssue со связанной целью, идентичностью и сохранённой важностью. Входные коллекции копируются, неизвестная цель проблемы и повторная идентичность отклоняются; результат и список метрик неизменяемы.

| Код | Значение | Полезное направление |
| --- | --- | --- |
| CLEAN_GOALS_SHARE | (активные цели − уникальные активные цели с проблемами) / активные цели × 100% | Рост |
| AFFECTED_GOALS_COUNT | Число уникальных активных целей хотя бы с одной проблемой | Снижение |
| ISSUES_COUNT | Общее число проблем активных целей | Снижение |

Проблемы разных КР одной цели увеличивают ISSUES_COUNT отдельно, но AFFECTED_GOALS_COUNT только один раз. Порядок метрик фиксирован таблицей. Счётчики точные, в MetricResult представлены BigDecimal без дробной части. Доля рассчитывается через BigDecimal и округляется до одного знака HALF_UP; при нулевом знаменателе null. Дельта вычитается из уже округлённых значений; для доли единица — процентные пункты. Например, 33.3 − 16.7 = 16.6 п.п.

Trend: IMPROVED, DETERIORATED или UNCHANGED в зависимости от знака дельты и полезного направления метрики. Нулевая показанная дельта даёт UNCHANGED, даже если исходная доля изменилась в пределах округления. Если current или previous равны null, delta и trend также null. Текущие счётчики 0 не подменяют отсутствующее сравнение.

По согласованному уточнению важность всех трёх метрик отражает самую серьёзную текущую проблему выбранной области: CRITICAL > MAJOR > MINOR, без проблем null. Порогов процентов/количества проблем не задано. Отдельно считаются точные current/previous/delta для critical/major/minor, в том числе нули; без прошлого снимка previous/delta равны null.

### Идентичность и дельта проблем

`IssueIdentity(ruleCode,objectType,objectId)` не включает прогон, подразделение, важность и связанную цель. Например, устаревший КР с тем же ID сохраняет идентичность при переносе между целями; замена КР новым ID создаёт новую проблему, даже если цель и количество проблем не изменились.

Для множеств текущих C и прошлых P проблем выбранной области: new = C \ P, persisting = C ∩ P, resolved = P \ C. Возвращаются мощности этих множеств. Без сравнения все три счётчика null; при двух пустых областях — 0. При переносе цели проблема может стать новой в подразделении назначения и исправленной в исходном, оставаясь сохраняющейся у общего родителя. Удаление и деактивация также исключают проблему из текущей области; resolved не доказывает ручного исправления нарушения.

### Проверочные значения демо

Для второго демопрогона относительно первого:

| Область | Доля сейчас / раньше | Целей с проблемами сейчас / раньше | Проблем сейчас / раньше | new / persisting / resolved |
| --- | --- | --- | --- | --- |
| U1 со всеми потомками | 65.2 / 65.2 | 8 / 8 | 8 / 10 | 3 / 5 / 5 |
| U2 вместе с U3 | 80.0 / 86.7 | 3 / 2 | 3 / 4 | 1 / 2 / 2 |
| U3 | 100.0 / 100.0 | 0 / 0 | 0 / 0 | 0 / 0 / 0 |

Текущая важность U1 и U2 — CRITICAL; U3 — null. Для U1 счётчики важности 3/2/3. Эти значения возвращаются через GET /api/kkd/summary.

## REST API

Все endpoint-ы читают данные. Запись источников и запуск прогонов через HTTP не предусмотрены; для прогонов используется отдельная команда. Авторизация и корпоративная интеграция не заданы. Контроллер не содержит SQL и расчётов: KkdController → прикладные сервисы → репозитории/чистый калькулятор.

RunQueryService предоставляет список прогонов и общую проверку существования/COMPLETED для SummaryService и IssueService. RunRepository добавляет проекцию RunDetails с временем начала/окончания; IssueRepository строит страницу и total с одинаковыми фильтрами. Пользовательские значения передаются параметрами SQL; динамические части запросов состоят только из фиксированных фрагментов.

DTO отделены от доменных моделей: ApiResponses содержит публичные формы ответов, ApiMapper преобразует даты, enum и поля. Имена полей — snake_case. Значения null не опускаются; числа остаются JSON numbers, а не строками. Даты — ISO YYYY-MM-DD, время — ISO 8601 с часовым смещением. Правила имеют верхний регистр, остальные перечисления — нижний. Текст message предназначен человеку; клиенту следует обрабатывать error.code.

### GET /api/runs

Параметров нет. Ответ 200 — JSON-массив всех прогонов, включая RUNNING и FAILED; пустой список — []. Порядок started_at DESC, id DESC. Поля элемента:

| Поле | Тип/смысл |
| --- | --- |
| id | Строковый ID прогона |
| snapshot_date | Дата снимка |
| status | running / completed / failed |
| compared_to_id | ID прошлого прогона либо null |
| started_at | Время начала |
| finished_at | Время окончания либо null |
| issues_count | Глобальное число проблем для COMPLETED, иначе null |
| error_code | Сохранённый код сбоя для FAILED, иначе null |

Пагинация списка прогонов не предусмотрена текущим контрактом; limit/offset относятся только к проблемам.

### GET /api/kkd/summary?run_id=...&unit_id=...

Оба параметра обязательны. Ответ 200 содержит ровно run, compared_to, unit, metrics, issues_by_severity, delta. run и compared_to — объекты {id,snapshot_date}, compared_to может быть null. unit содержит {id,name,parent_id} из текущего снимка. previousUnit остаётся внутренней информацией прикладного сервиса, отдельного поля в HTTP нет.

Контракт сверен с InternBTBack.pdf, страницы 2–3. Метрики идут в порядке clean_goals_share, affected_goals_count, issues_count. Каждый элемент: {key,title,unit,value,previous,delta,trend,severity}. unit — "%" у доли и "шт." у счётчиков; value — текущее значение. Trend — better/worse/unchanged либо null. Внутренние MetricCode/MetricTrend и MetricResult.current сохраняют доменные имена; ApiMapper явно переводит их в контракт БТ. severity — дополнительное согласованное поле, critical/major/minor либо null. Дополнительное unit.parent_id также сохранено; обязательные поля фрагмента БТ не заменяются расширениями.

issues_by_severity — массив трёх элементов в порядке critical, major, minor: {code,current,previous,delta}. Current берётся из текущего снимка области, previous — из прошлого снимка той же области, delta=current−previous. QualityMetricsCalculator возвращает оба SeverityCounts; ApiMapper формирует строки сравнения. У первого прогона previous/delta равны null для каждой важности, current остаётся числом. Если прошлый прогон существует, но подразделение в нём отсутствует, предыдущие счётчики равны 0. Нулевые текущие уровни не исключаются из массива. delta верхнего уровня содержит new/persisting/resolved; у первого прогона все три поля null.

Пример для второго демопрогона и U1:

```json
{

  "compared_to": {"id": "demo-2026-10-19", "snapshot_date": "2026-10-19"},
  "unit": {"id": "U1", "name": "Банк", "parent_id": null},
```

| Параметр | Обязательность и ограничения |

### Валидация и ошибки

RequestParameters получает MultiValueMap, чтобы обнаружить повторения. На каждом endpoint-е разрешены только перечисленные параметры; неизвестные, повторные и пустые значения отклоняются. Значения с NUL (в URL — %00) также отклоняются с 422 INVALID_PARAMETER до обращения к БД; иначе PostgreSQL отверг бы строковый параметр и запрос превратился бы в 500. ID не обрезаются и не преобразуются в UUID. Числа содержат только десятичные цифры без знака, пробелов или дробной части и должны помещаться в int. Валидация запроса предшествует обращениям к прикладным сервисам.

Ошибки обработки API возвращаются в JSON с единственной оболочкой:

```json
{"error":{"code":"INVALID_PARAMETER","message":"limit must be between 1 and 200"}}
```

| HTTP | code | Условие |
| --- | --- | --- |
| 404 | RUN_NOT_FOUND | Нет прогона |
| 404 | UNIT_NOT_FOUND | Нет подразделения в текущем снимке |
| 404 | NOT_FOUND | Нет маршрута |
| 422 | INVALID_PARAMETER | Ошибка параметров |
| 422 | RUN_NOT_COMPLETED | Запрошена сводка/проблемы RUNNING или FAILED |
| 405 | METHOD_NOT_ALLOWED | Метод не поддерживается; сохраняется Allow |
| 406 | NOT_ACCEPTABLE | Accept не допускает JSON |
| 500 | INTERNAL_ERROR | Непредвиденная ошибка; message=Internal server error |

ApiExceptionHandler расширяет ResponseEntityExceptionHandler для единой формы framework-ошибок и прикладных исключений. В ответ 500 не попадают SQL, пароли, имена исключений или трассировки; в журнал записывается только класс неожиданной ошибки. Ошибка серверной логики IllegalArgumentException не маскируется под неверный пользовательский параметр: в 422 преобразуются только ошибки разбора контролируемых входных значений.

## Контейнерный запуск и готовность

Dockerfile собирает JAR Maven Wrapper-ом на Temurin JDK 21 и копирует только JAR в Temurin JRE 21. Оба базовых образа Java закреплены digest списка платформ. Сборочный контекст ограничен исходниками и Maven-конфигурацией; .env, Git и кэши исключены. Runtime: UID/GID 10001, read-only root, tmpfs /tmp, без Linux capabilities, no-new-privileges. Секрет БД передаётся при запуске, в образ не записывается.

Compose ожидает service_healthy БД перед запуском приложения. Внутренние порт 8080 и JDBC db:5432 фиксированы, SERVER_PORT/DB_PORT меняют только порты localhost хоста. COMPOSE_DEMO_ENABLED по умолчанию true; KKD_RUN_ENABLED принудительно false. Локальный KKD_DEMO_ENABLED не управляет Compose. Запуск docker compose up работает без .env: БД/пользователь kkd, пароль kkd_local_example, порты 8080/5432 на localhost. Это параметры локального демо. Необязательная .env и переменные окружения переопределяют значения; при локальном запуске Java по-прежнему требуется экспортировать DB_PASSWORD.

Именованный том PostgreSQL сохраняет источники и историю; повторное демо использует уже готовую пару. Изменение начальных POSTGRES_* не перенастраивает существующий том.

Spring Boot Actuator использует версию BOM. Все endpoint-ы закрыты через access.default=none, кроме health с read-only доступом и web exposure health. Discovery выключен; show-details и show-components — never. Пробы включены вне Kubernetes. Readiness-группа включает readinessState и db: до окончания ApplicationRunner трафик не принимается, после старта без БД — 503 DOWN. Liveness не включает БД. Формат ответов health — стандартный Actuator, а не прикладная оболочка error. Docker HEALTHCHECK обращается к /actuator/health/readiness; Compose --wait дожидается healthy. В Compose Hikari connection-timeout=2000 мс позволяет readiness быстро вернуть недоступность БД.

CI на Ubuntu 24.04/JDK 21 выполняет Maven verify с Testcontainers, затем scripts/check_compose.py. Скрипт создаёт отдельный случайный Compose-проект, собирает образ, проверяет реальный HTTP и данные, отсутствие дублей после перезапуска, readiness/liveness при остановке и восстановлении БД. Собственные контейнеры и том удаляются в finally. Docker build пропускает исполнение тестов, поскольку verify уже проверяет их на runner; форматирование и требование JDK остаются активны. Actions закреплены SHA, workflow имеет только contents:read; отчёты и JAR хранятся 7 дней. Удалённое выполнение подтверждено для 5afaace: [успешный запуск GitHub Actions](https://github.com/wow-vulpes/InternSberBackend/actions/runs/41178861616) (31 октября 2026), включая verify, контейнерную проверку и загрузку артефактов.
