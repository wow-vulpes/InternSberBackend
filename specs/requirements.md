# Требования к модулю ККД

Источники: БТ.pdf (конкретное backend-тестовое), БТ2.pdf (контекст корпоративного проекта), уточнения пользователя в чате. Дедлайн — 8 ноября 2026, желательно раньше.

## Согласованный объём

Backend на Java, PostgreSQL, REST API, миграции, демонстрационные данные, тесты и документация. Фронтенд исключён пользователем. Storybook, исходные сервисы, требования команды и доступ к ИФТ не предоставлены. Соответствие интерфейсу, интеграцию и установку на ИФТ подтвердить нельзя; эти условия не считаются выполненными локальной проверкой.

## Требования и приёмка

| ID | Требование | Критерий приёмки |
| --- | --- | --- |
| REQ-01 | Четыре правила: GOAL_NO_OWNER (critical), GOAL_NO_KR (critical), KR_WEIGHTS_SUM (major), KR_STALE_PROGRESS (minor) | Правила работают отдельно от API/SQL; применяются только к активным целям и их КР; граничные тесты |
| REQ-02 | PostgreSQL: иерархия подразделений, цели, КР, правила, прогоны, проблемы и снимки | Ограничения целостности, стабильные ID объектов, история не меняется при изменении исходных данных |
| REQ-03 | Минимум три метрики по подразделению с потомками; сравнение прогонов | Текущие/прошлые значения, дельта, направление, важность, новые/сохраняющиеся/исправленные; у первого прогона сравнение null |
| REQ-04 | GET /api/runs, GET /api/kkd/summary, GET /api/kkd/issues | Поля по БТ; фильтры проблем по подразделению, правилу, важности; limit, offset, total; стабильный порядок |
| REQ-05 | Валидация и единый формат ошибок | Неизвестные прогон/подразделение — 404, некорректные параметры — 422; {"error":{"code":"...","message":"..."}} |
| REQ-06 | Демонстрационные данные | 24 цели, 3 подразделения, 2 прогона; нарушения всех правил, примеры всех категорий изменений; перезапуск не дублирует данные |
| REQ-07 | Liquibase, SQL-объекты и откат | Накат → откат → повторный накат на PostgreSQL без ошибок; документированная воспроизводимая проверка |
| REQ-08 | Запуск одной командой | docker compose up поднимает приложение, PostgreSQL, миграции и демонстрационные данные |
| REQ-09 | Автоматические проверки | JUnit 5: минимум два правила на границах, метрика, дельта; тесты БД/миграций и контрактов на соответствующих шагах |
| REQ-10 | Документация и прозрачность использования ИИ | README с запуском, тестами, откатом, архитектурой и ссылкой на specs/; актуальные requirements.md и design.md |

Стек: Java 21 (БТ разрешает 17+), Spring Boot 3, Maven, PostgreSQL 17 (БТ разрешает 15+), Liquibase. Конфигурация через переменные окружения и .env.example. Контроллеры отделены от бизнес-логики и доступа к данным.

## Проектные решения, принятые в согласованном дизайне

Это уточнения для реализации, а не дословные требования БТ. Изменять после согласования.

- BR-01: отсутствующий ответственный — null, пустая или пробельная строка.
- BR-02: активная цель без КР даёт GOAL_NO_KR, без дополнительного KR_WEIGHTS_SUM.
- BR-03: при наличии КР сумма весов сравнивается с 100 точно через BigDecimal.
- BR-04: KR_STALE_PROGRESS — более 45 календарных дней до даты снимка; ровно 45 допустимо; отсутствующая дата обновления факта — нарушение.
- BR-05: неактивные цели и их КР исключаются из правил и метрик качества.
- BR-06: подразделение включает всех потомков; каждая цель учитывается один раз.
- BR-07: доля корректных целей = активные цели без проблем / все активные цели × 100%; проблемы КР делают связанную цель некорректной. Округление до одного десятичного знака; при нулевом знаменателе null.
- BR-08: ещё две метрики — число уникальных активных целей с проблемами и общее число проблем. Рост доли корректных целей — лучше; снижение двух счётчиков — лучше. При равенстве trend=unchanged; без сравнения trend=null. Дельта процента выражается в процентных пунктах; порядок округления уточнить в дизайне шага 5.
- BR-09: идентичность проблемы — (rule_code, object_type, object_id). Сравниваем с предыдущим успешно завершённым прогоном. Первый прогон: compared_to, previous, delta и счётчики new/persisting/resolved равны null.
- BR-10: фильтр подразделения использует иерархию соответствующего снимка; исторические данные не пересчитываются по текущей структуре.
- BR-11: каждый запуск создаёт новый прогон; завершённый прогон неизменяем. Частичные результаты не выдаются за завершённые.

## Ещё предстоит детализировать

- Контракты ответов runs/issues, статусы прогонов, сортировка, пределы пагинации.
- Обработка некорректных исходных данных (веса, даты, циклы иерархии), транзакции и конкурирующие запуски.
- Команда запуска прогонов и необязательное еженедельное расписание, выключенное по умолчанию.
- Назначение представления и SQL-функции иерархии; необходимость дополнительных процедур.
- Аутентификация и интеграция с корпоративной системой не заданы; не описывать их как реализованные.
