# Требования к модулю ККД

Источники: InternBTBack.pdf (тестовое Backend-разработчика, 3 страницы), InternBT.pdf (корпоративный проект, 2 страницы), согласованные уточнения объёма. Оригиналы повторно прочитаны 31 октября 2026. Документ содержит требования ко всему решению; фактическая готовность отражена в таблице покрытия.

## Объём

Объём раздела «Тестовое задание» InternBTBack.pdf: Java-сервис, PostgreSQL, REST API для страницы ККД, миграции, демонстрационные данные, тесты и документация. Создание frontend в этом перечне не требуется; упоминание страницы в бизнес-кейсе описывает корпоративный TO BE. InternBT.pdf относится к полному проекту со страницей, Storybook, существующими сервисами и ИФТ. Эти корпоративные условия не считаются выполненными тестовым backend-сервисом.

## Правила и проектные решения

Ниже приведены принятые уточнения неоднозначных требований. Они отделены от исходных критериев задания и определяют ожидаемое поведение реализации.

- BR-01: отсутствующий ответственный — null, пустая или пробельная строка.
- BR-02: активная цель без КР даёт GOAL_NO_KR, без дополнительного KR_WEIGHTS_SUM.
- BR-03: при наличии КР сумма весов сравнивается с 100 точно через BigDecimal.
- BR-04: KR_STALE_PROGRESS — более 45 календарных дней до даты снимка; ровно 45 допустимо; отсутствующая дата обновления факта — нарушение.
- BR-05: неактивные цели и их КР исключаются из правил и метрик качества.
- BR-06: подразделение включает всех потомков; каждая цель учитывается один раз.
- BR-07: доля корректных целей = активные цели без проблем / все активные цели × 100%; проблемы КР делают связанную цель некорректной. Округление до одного десятичного знака; при нулевом знаменателе null.
- BR-08: ещё две метрики — число уникальных активных целей с проблемами и общее число проблем. Рост доли корректных целей — лучше; снижение двух счётчиков — лучше. При равенстве trend=unchanged; без сравнения trend=null. Дельта процента выражается в процентных пунктах. Доля округляется до одного десятичного знака HALF_UP; дельта — разность округлённых текущего и прошлого значений. trend определяется по показанным значениям: better/worse/unchanged, с учётом полезного направления изменения.
- BR-09: идентичность проблемы — (rule_code, object_type, object_id). Сравниваем с предыдущим успешно завершённым прогоном. Первый прогон: compared_to, previous, delta и счётчики new/persisting/resolved равны null.
- BR-10: фильтр подразделения использует иерархию соответствующего снимка; исторические данные не пересчитываются по текущей структуре.
- BR-11: каждый запуск создаёт новый прогон; завершённый прогон неизменяем. Частичные результаты не выдаются за завершённые.
- BR-12: null вместо набора целей/даты снимка/элемента списка/списка КР, пустые обязательные ID, отсутствующий вес КР, повторные ID целей или КР — некорректный вход, отклоняемый через IllegalArgumentException без частичного результата. ID цели и КР могут совпадать между типами. Ответственный и дата обновления факта могут отсутствовать: это данные для правил, а не ошибка входного контракта.
- BR-13: будущая дата обновления не считается устаревшей; диапазон отдельного веса не проверяется выбранными правилами, только сумма. Результат неизменяемый, порядок: goalId → ruleCode.name() → objectType.name() → objectId; повторный вызов с теми же данными даёт тот же результат.
- BR-14: снимки и проблемы связаны внутри прогона и независимы от текущего источника; терминальные прогоны COMPLETED/FAILED и их данные неизменяемы обычными DML-операциями. Запись сериализуется с завершением блокировкой строки прогона.
- BR-15: новый прогон только RUNNING; завершение требует finished_at, FAILED также непустую ошибку. Сравнение только с COMPLETED с датой не позже текущей. Идентичность и ссылка сравнения неизменяемы.
- BR-16: обязательные связи, конечные числа/даты и непустые ID контролирует БД; отсутствие owner/даты обновления допустимо для правил. Циклы иерархии снимка запрещают COMPLETED. VIEW показывает счётчики только COMPLETED, частичные результаты — null.

- BR-17: обычные прогоны сериализуются общей транзакционной advisory-блокировкой. Для сравнения выбирается последний по времени завершения успешный прогон с датой снимка не позже текущей; при равном времени — ID по убыванию. Повторный обычный вызов создаёт новый ID.
- BR-18: снимок согласован за счёт блокировок всех трёх таблиц источника. Ошибка захвата/правил/сохранения откатывает все частичные результаты и сохраняет FAILED с null-счётчиком; ошибки инфраструктуры до создания строки или при commit могут откатить весь прогон.
- BR-19: демо включается явно, создаёт два фиксированных прогона через обычные правила в одной транзакции и не дублируется при повторном/одновременном старте. Заполненная БД без завершённой демопары отклоняется без изменений.
- BR-20: обычная команда принимает дату снимка YYYY-MM-DD, по умолчанию — сегодня UTC. Демо и одиночный прогон взаимоисключающие; обычный старт без этих флагов не создаёт прогонов.

- BR-21: важность каждой метрики равна максимальной сохранённой важности текущих проблем в выбранной области (CRITICAL > MAJOR > MINOR); без проблем — null. Это согласованное уточнение, пороги по значениям метрик не вводятся.
- BR-22: сравнение использует сохранённый compared_to_id, а не последний прогон на момент запроса. Корень и потомки берутся отдельно из каждого снимка. Если подразделения раньше не было, прошлые счётчики равны 0, прошлая доля — null; ссылка на прогон сравнения сохраняется.
- BR-23: новые/сохраняющиеся/исправленные определяются разностью/пересечением множеств идентичностей проблем в выбранной области каждого снимка. Перенос, удаление или деактивация цели могут убрать проблему из этой области; «исправленная» означает отсутствие в текущей выборке, а не обязательно ручное исправление исходных данных.
- BR-24: метрики доступны только для COMPLETED; RUNNING/FAILED отклоняются явной ошибкой состояния. Неизвестный текущий прогон/подразделение — явная ошибка поиска. При нулевом числе активных целей доля, её delta и trend равны null; счётчики остаются определены. Если хотя бы одно значение метрики не определено, её delta и trend равны null.

- BR-25: JSON API использует snake_case; статусы, типы объектов, метрики, тренды и важности — строчные значения, коды правил — точные имена enum в верхнем регистре. Значения null сохраняются в ответах. run_id обязателен для сводки/проблем; unit_id обязателен для сводки, необязателен для проблем. ID не нормализуются и не ограничиваются UUID.
- BR-26: список прогонов включает все статусы, порядок started_at DESC → id DESC; счётчики RUNNING/FAILED равны null. Сводка и проблемы выдаются только для COMPLETED; другое состояние — 422 RUN_NOT_COMPLETED.
- BR-27: фильтры unit_id/rule/severity для проблем объединяются через AND; unit_id включает потомков снимка. limit по умолчанию 50, диапазон 1–200; offset по умолчанию 0, диапазон 0–2147483647. total вычисляется после фильтров до пагинации. Порядок проблем: goal_id → rule_code → object_type → object_id. За концом выборки items=[], total сохраняется.
- BR-28: неизвестные, повторные, отсутствующие обязательные и пустые параметры, неверные числа/правила/важности и значения с NUL — 422 INVALID_PARAMETER. Важность в фильтре регистронезависима; код правила — регистрозависим. Неизвестные ресурсы — 404 RUN_NOT_FOUND/UNIT_NOT_FOUND. Ошибки API имеют только error.code/message; непредвиденные ошибки — 500 INTERNAL_ERROR без SQL, паролей или трассировок.

- BR-29: docker compose up не требует .env или предварительного задания переменных. Compose использует локальные БД/пользователя kkd и пароль kkd_local_example; оба порта опубликованы только на localhost. Для других параметров доступны переменные окружения и необязательный .env. Compose по умолчанию включает демо через COMPOSE_DEMO_ENABLED, дожидается здоровой БД и готового приложения. Readiness зависит от завершения запуска и доступности БД; liveness от БД не зависит. Открыт только Actuator health, без деталей. Обычный локальный Java-старт не создаёт демо без явного флага.

- BR-30: публичный контракт summary следует фрагменту InternBTBack.pdf: key вместо code, value вместо current, unit="%"/"шт.", trend=better/worse/unchanged/null. issues_by_severity — три строки {code,current,previous,delta}; без прошлого прогона previous/delta=null, с отсутствующим прошлым подразделением previous=0. Дополнительные severity метрики и parent_id подразделения сохранены как согласованные расширения.

## Границы реализации

Реализован перечень задач backend-тестового InternBTBack.pdf (стр. 1–3). Выбраны четыре правила из шести: CASCADE_NO_PARENT и KR_NO_TARGET не требуются дополнительно. Создание самой страницы не входит в перечень задач этого тестового.

| Условие полного корпоративного проекта InternBT.pdf | Граница самостоятельного backend-решения |
| --- | --- |
| Страница статистики, проблем и дельты по Storybook | Предоставлен REST API для страницы; frontend и проверка макетов не выполнялись |
| Endpoint-ы в существующих Java-сервисах | Создан отдельный Spring Boot сервис; перенос требует исходников и контрактов корпоративного проекта |
| ККД по существующим данным | Проверяются текущие таблицы источников PostgreSQL; подключение реальных источников требует их схемы и правил сопоставления |
| Таблицы / VIEW / функции и процедуры | Есть таблицы, VIEW и SQL/PLpgSQL-функции; прогоны выполняются Java-компонентом. Обязательного CREATE PROCEDURE в backend-тестовом нет |
| Оформление по правилам команды | Применён единый формат Java; корпоративные правила не предоставлены |
| Установка сервиса и цикл миграций на ИФТ | Сборка и накат/откат/повторный накат проверены на PostgreSQL 17.11 локально и в CI; доступ к ИФТ отсутствует |

Автоматический еженедельный запуск и авторизация не реализованы. В backend-тестовом нет отдельного обязательного пункта реализации планировщика; доступна команда нового прогона. Корпоративные способ запуска, авторизация и интеграция требуют уточнения при внедрении. Windows отдельно не проверен.

## Результаты проверки

На 31 октября 2026 полный Maven verify завершён успешно: 259 сценариев без ошибок и пропусков, исполняемый JAR собран. Из них 122 доменных, 7 проверок команд, 3 проверки обработки ошибок и 127 с PostgreSQL. Проверки включают контракт summary из оригинального PDF: key/unit/value, better/worse/unchanged, массив важностей current/previous/delta и null первого сравнения. NUL (%00) в параметрах отклоняется с 422 до обращения к БД.

Проверка миграций сравнивает таблицы, колонки, ограничения, индексы, функции, триггеры и VIEW после наката и повторного наката. Отдельно выполнены Maven update → rollback к kkd-baseline → update → update и запуск JAR на уже мигрированной БД без изменения служебной истории. Проверены 9 бизнес-таблиц, 4 правила и 5 записей Liquibase; после отката бизнес-схема отсутствует, служебная история пуста.

На Linux проверены чистая копия исходников, новый том БД, сохранение истории после down/up, отсутствие дублей демо, отдельный прогон и восстановление приложения после отказа БД. Запуск без .env и без экспортированных параметров БД также проверен в отдельной чистой папке; для изоляции использованы случайные внешние порты. Сеть и Docker-кэш были доступны. Пользовательские БД не использовались, временные контейнеры и тома удалены.

Команды воспроизведения и результаты демо — в [README](../README.md). Контейнерная проверка — scripts/check_compose.py. Успешный опубликованный [workflow](https://github.com/wow-vulpes/InternSberBackend/actions/runs/41183777860) относится к 9c831e1 и покрывает исправленный контракт summary. Последующие изменения требуют проверки CI для нового коммита.

## Организационные условия сдачи

Сдача — ссылка на репозиторий в блоке «О себе» резюме. Мотивация, роль и готовность к согласованному графику описаны в конце [README](../README.md#мотивация-участия-в-проекте). Конкретные часы в неделю и период участия согласуются с командой. В backend-ТЗ указан срок выполнения 3 дня; актуальный срок подачи определяется договорённостью с организатором.
