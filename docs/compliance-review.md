Дата: 31 октября 2026. Прочитаны полностью InternBTBack.pdf (3 страницы, backend-тестовое) и InternBT.pdf (2 страницы, описание корпоративного проекта). ## Что относится к тестовому

Раздел «Тестовое задание» в InternBTBack.pdf, страницы 1–2, требует Java-сервис, БД и REST API для страницы ККД. Создание самой страницы, интеграция в существующий корпоративный репозиторий и внедрение на ИФТ описаны в общем бизнес-кейсе и InternBT.pdf; они не перечислены как самостоятельные deliverables backend-тестового. Поэтому отсутствие frontend не является выявленной ошибкой backend-тестового. Полное выполнение корпоративного проекта при этом не заявляется.

## Найденные расхождения и исправления

Предыдущая спецификация ошибочно зафиксировала JSON, отличающийся от оригинального фрагмента БТ. Прежняя проверка только по этой спецификации не могла подтвердить соответствие оригиналу; после получения PDF контракт исправлен.

| Требование InternBTBack.pdf, стр. 2–3 | Было | Исправлено |
| --- | --- | --- |
| Идентификатор метрики key | code | key |
| Текущее значение value | current | value |
| Единица метрики unit | Отсутствовала | "%" для доли, "шт." для двух счётчиков |
| Признак лучше/хуже; пример trend=worse | improved/deteriorated | better/worse; unchanged при равенстве, null без сравнения |
| issues_by_severity — массив {code,current,previous,delta} | Объект только с текущими critical/major/minor | Массив трёх уровней с текущими/прошлыми значениями и дельтой |
| Первый прогон: прошлые значения и дельты null | Для разбивки по важности полей не было | previous/delta=null у каждого уровня первого прогона |

Прошлая разбивка считается по прошлому снимку выбранного подразделения с потомками, а не по текущим данным. Если прошлый прогон есть, но подразделения в нём ещё не было, previous=0 для каждой важности. Нулевые уровни сохраняются в ответе. Дополнительные severity метрики и parent_id подразделения оставлены как согласованные расширения фрагмента БТ; обязательные поля не заменяются ими.

Исправление предыдущей проверки также сохранено: NUL (%00) в run_id/unit_id теперь даёт 422 INVALID_PARAMETER до обращения к БД вместо 500. Это соответствует требованию корректной валидации. Исходный PostgreSQL не допускает NUL в строках: [документация PostgreSQL 17](https://www.postgresql.org/docs/17/datatype-character.html).

## Доказательства после исправления

- Три проверки сводки, переписанные по оригиналу БТ, не проходили до изменения кода: два нарушения контракта и одна ошибка обращения к отсутствующему полю.
- После исправления полный Maven verify завершился успешно: 259 тестов, без ошибок и пропусков; JAR собран. Проверены первый прогон, U1, подразделение U2 с потомками и новое пустое подразделение.
- На демо U1 разбивка теперь равна critical 3/5/−2, major 2/2/0, minor 3/3/0 (current/previous/delta). Для U2 — 1/2/−1, 0/1/−1, 2/1/+1. Это подтверждает как положительную, так и отрицательную дельту важности.
- Реальные HTTP-запросы в Compose проверяют key/unit/value, better, массив важностей и null первого прогона. Перезапуск без дублей, отказ/восстановление БД и %00 также пройдены; временный проект и том удалены.
- Миграции не менялись. Старые сохранённые прогоны остаются пригодны: новый ответ строится из уже существующих снимков. Старый JSON-контракт изменён намеренно для соответствия оригиналу БТ; клиентам прежнего формата потребуется обновление.
- Новый GitHub Actions для этих изменений ещё не подтверждён. Ранее успешный workflow для 5afaace не проверял исправленный контракт.

## Что требует действий кандидата или организатора

1. **Ссылка в резюме.** Backend-ТЗ, стр. 1, требует указать репозиторий в разделе «О себе». Резюме не предоставлено; внесение ссылки не проверено.
2. **Мотивация.** На стр. 3 запрошены ответы: почему интересен проект, как кандидат видит роль в команде, сколько часов в неделю и на какой период готов участвовать. Личные ответы не предоставлены; их нельзя заменить выдуманными сведениями.
3. **Срок.** В PDF указаны 3 дня; в переписке назван дедлайн до 8 ноября. Необходимо опираться на фактическую договорённость с организатором; код не разрешает это расхождение.
4. **Корпоративное внедрение.** InternBT.pdf требует страницу по Storybook, интеграцию в существующие сервисы/источники, оформление по правилам команды и проверки на ИФТ. Материалы и доступ не предоставлены. Это граница внедрения полного проекта, а не основание добавлять произвольный frontend в backend-тестовое.
5. **SQL-процедуры и еженедельный запуск.** В корпоративном описании упомянуты функции/процедуры и планируемая еженедельная проверка. Backend-ТЗ требует четыре независимых правила в Java-компоненте и не устанавливает обязательный CREATE PROCEDURE или автоматический планировщик. Сейчас есть SQL-функции/VIEW и отдельная команда Java; корпоративный способ запуска требует уточнения при интеграции.

Итог: после исправления JSON-контракта техническая часть самостоятельного backend-тестового соответствует проверенным обязательным пунктам PDF. Организационные действия кандидата и приёмка полного корпоративного проекта перечислены отдельно и не объявляются выполненными.
